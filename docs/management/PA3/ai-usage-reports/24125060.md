## 2. My role and involvement

I drove the decisions; the AI ran the bulk mechanical work. The recurring pattern was that *I* decided what the admin side should or should not do, and the AI's job was to find every place in the sprawling spec set that still said the old thing and bring it into line.

**What I owned and decided**

- **Admin screen architecture.** I decided the admin app is organised under eight top-level tabs — Dashboard, Circulation, Books, Acquisitions, Queues, People, Money, Reports — and that the top universal search bar should be removed in favour of a bell (notifications) and a profile block. The UI files for this live under `docs/analysis-and-design/Admin UI Master Design.md`.
- **Scope reduction, feature by feature.** I decided each simplification, and the AI propagated it across the artefacts. Highlights I chose:
  - Dashboard shows only 8 key metrics + a monthly-loan trend chart, and **no "Bottom 10 (Zero-Loan)" ranking** (this conflicted with UC-27's top-10-only ranking).
  - Reports became 3 preset export modules with only a date-range option — no table previews or fancy filters.
  - Circulation, Books, Acquisitions, Queues, People and Money became a single "master table + side detail panel" design.
  - Book batch CSV import only previews erroneous rows; batch ingestion itself is not directly exposed.
  - Patron history only tracks tier changes, account status and strikes — no dedicated audit trail, no per-student receipts tab (receipts are deferred to Money).
  - Acquisition was stripped of pricing estimation and third-party/provider lookup; a batch is hand-created, each title pulled from student suggestions, tracked only by quantity, and "received" is a glorified checklist with no partial shipments.
  - Counter payment became: list charges → optional note + amount → confirm, which closes the charge and emits a receipt.
  - The dedicated staff "resolve lost book" flow was removed; statuses are edited inline in the Books screen's copies tab, and write-off slips are now the *only* way to retire a book from circulation.
- **Membership plan constraints.** I removed the admin's ability to create and deactivate plans entirely; admins may only edit the policies of the standard unpaid rank and the yearly premium tier.
- **Use-case corrections.** I clarified UC-31's flow (the detailed tab still exposes four actions: set inactive, restore, membership refund/termination, and register/renew), and established the rule that a use-case spec only *states* what a flow does — removing a feature from the product must not turn into "this use case has no A or B" text.
- **Authorship.** I directed that every UC file changed in the scope pass be given a revision-history row authored by me (`Nguyễn Anh Khôi`, version 1.1), rather than silently rewriting teammates' drafts.

**How I checked and corrected the AI**

- I caught a teammate's earlier claim reappearing in my agent: that UC-27 "excludes least-borrowed rankings", which the agent had to re-verify against the actual spec before I accepted the Dashboard change.
- I flagged a real cross-artefact inconsistency myself — UC-18 said lost-copy status changes happen in Books, but the text still retained a Circulation mention — and had the AI reconcile it rather than paper over it.
- I rejected the "edit the use-case spec to say a feature doesn't exist" reflex twice and restated the rule until the edits conformed.
- I repeatedly pushed back on over-simplified one-line summaries of a flow and asked for the concrete step structure (e.g. UC-31's four detail actions) before accepting a rewrite.

**What I delegated to the AI**

Finding every mention of a removed feature across the use-case specs, the FULLSPEC, the per-feature Spec Kit files and the catalogue; proposing a tab grouping during the UI reorganisation; and applying the mechanical edits. I did not accept the edits on trust — each removal was checked against my intent (see §5).

## 5. Assessment

**Where AI added real value**

- **Cross-artefact propagation.** A single scope decision ("no third-party provider lookup", "no Bottom 10 ranking", "admins can't create plans") had to land consistently in the use-case spec, the catalogue, the diagram, the FULLSPEC and the per-feature spec. Doing that by hand is where omissions silently creep in; the AI swept all of them in one pass.
- **Restructuring a messy inventory.** The admin screen inventory was inconsistent and hard to parse; grouping it into eight tabs and a consistent "table + detail panel" pattern made it reviewable.
- **Checking consistency instead of assuming it.** The AI was able to surface the UC-27 / Dashboard conflict and the UC-18 Books-vs-Circulation inconsistency because it could diff one artefact against another, which is exactly the kind of drift I would have missed on a single read-through.

**Where AI was unreliable**

- **Echoing a stale claim from another session.** A teammate's earlier "UC-27 excludes least-borrowed rankings" phrasing resurfaced and had to be re-verified against the actual spec before I trusted it — the claim was about a *different* iteration of the spec.
- **Reflexive "state the absence" edits.** Removing a feature initially produced prose like "this use case has no pricing step", which is the wrong edit — the spec should simply describe what the flow *does*. I had to state the rule twice.
- **Over-summarising flows.** The AI tended to compress a flow into a one-liner, flattening exactly the step structure (e.g. UC-31's four distinct detail actions) that a use-case spec exists to preserve.

**Division of responsibility.** All "what should the admin side be able to do" decisions were mine; the AI's outputs became part of the project only after I confirmed each removal matched my intent and the revision history correctly attributed the change to me.

**Net effect.** The admin side of ShelfHelp went from an over-scoped, internally inconsistent collection of flows to a leaner, coherent set that the team can actually build — with the scope decisions and their authorship documented so a reviewer can trace why each feature shrank.
