## 1. Use-Case Name

**UC-26 - Review inventory history** (Traces to: `FEAT-22`, `FR-INV-05`, `FR-INV-06`, `TS-51`)

### 1.1 Brief Description

This use case enables a Librarian (Admin) to inspect the complete, immutable chronological audit trail of all physical copy inventory mutations. This includes batch shipment receipts, manual copy additions, status transitions (e.g., available, held, borrowed, under repair, damaged), write-offs, and automatic or manual lost designations. Staff can search across books, apply quick categorical filters, drill down into an individual barcode's lifecycle, follow direct links to reference documents (acquisition batches, write-off slips, or loan records), and export filtered audit records to CSV, PDF, or Excel formats for administrative accounting and compliance audits.

### 1.2 Actors

- **Primary Actor:** Librarian (Admin)
- **Supporting Actor:** PostgreSQL Database & Report Generation Engine

## 2. Flow of Events

### 2.1 Basic Flow

This use case begins when an authenticated **Librarian (Admin)** accesses the Inventory History screen (`/admin/inventory-history`) from the library administration portal.

1. The **Librarian (Admin)** navigates to the "Inventory History" section via the main administrative navigation sidebar.
2. The **System** queries the immutable `inventory_transactions` log table, joining book metadata and staff profile tables.
3. The **System** displays the inventory audit log page featuring:
   - Search input (book title, author, ISBN, or copy barcode).
   - Date range pickers (Start Date, End Date).
   - Quick category filters: "All", "Batch receipts", "Manual additions", "Stock reductions", "Status changes".
   - A paginated data table (default newest first, 50 rows per page) showing columns: `Timestamp`, `Operator` (Staff name or `system`), `Book Title / ISBN`, `Barcode / Copy #`, `Transaction Type`, `Delta` (e.g., `+1`, `-1`, `0`), `Reason`, and `Reference Link`.
   - Export action buttons (`Export CSV`, `Export PDF`, `Export Excel`).
4. The **Librarian (Admin)** reviews the displayed log entries to verify recent book stock modifications, stock intake numbers, or loss write-offs.
5. The **Librarian (Admin)** finishes reviewing and navigates away or closes the view. The use case ends.

### 2.2 Alternative Flows

#### 2.2.1 Filter by Transaction Category

_Branching point: At Step 3 of the Basic Flow, if the Librarian wishes to narrow results by transaction type or date range._

1. The **Librarian (Admin)** selects a quick filter tab (e.g., "Stock reductions" or "Batch receipts") or specifies a custom date range.
2. The **System** issues an indexed query filtering records by `type` enum (`batch_receipt`, `manual_addition`, `found`, `write_off`, `lost`, `status_change`) and the specified date range.
   - For "Stock reductions", the system presents both manual write-off entries (`write_off`) and automatic or staff-flagged lost entries (`lost`).
3. The **System** updates the data table view and displays the count of matching audit transactions.
4. The flow resumes at Step 4 of the Basic Flow.

#### 2.2.2 Drill Down to Specific Physical Copy History

_Branching point: At Step 3 of the Basic Flow, if the Librarian searches for a specific barcode or clicks a copy barcode in the table._

1. The **Librarian (Admin)** enters a specific copy barcode into the search filter or clicks a barcode link in a table row.
2. The **System** filters the audit log strictly to transactions tied to that physical copy ID.
3. The **System** displays the copy's full lifecycle in chronological order: initial intake (`batch_receipt` or `manual_addition`), subsequent loan status changes (`available` -> `held` -> `borrowed` -> `returned`), condition updates (`good` -> `damaged`), and any terminal slip write-offs (`retired`).
4. The **Librarian (Admin)** completes inspection of the copy lifecycle and clears the copy filter to return to the global log.
5. The flow resumes at Step 4 of the Basic Flow.

#### 2.2.3 Navigate to Source Reference Record

_Branching point: At Step 3 of the Basic Flow, if the Librarian inspects the origin of an inventory change._

1. The **Librarian (Admin)** clicks the hyperlink in the `Reference Link` column of a specific transaction row (e.g., batch reference `PO-2026-004`, write-off slip `WO-2026-012`, or loan item `LI-8921`).
2. The **System** resolves the target reference and opens the corresponding detail screen in a new modal or tab:
   - For `batch_receipt`: Opens Acquisition Batch Detail (`/admin/batches/:id`).
   - For `write_off`: Opens Write-Off Slip Detail (`/admin/writeoffs/:id`).
   - For `lost` or `status_change` tied to a loan: Opens Loan / Circulation Detail (`/admin/circulation/:id`).
3. The **Librarian (Admin)** verifies the underlying source documents and returns to the Inventory History view.
4. The flow resumes at Step 4 of the Basic Flow.

#### 2.2.4 Export Audit Log to File

_Branching point: At Step 3 of the Basic Flow, if the Librarian requires an offline report for accounting or stocktaking verification._

1. The **Librarian (Admin)** clicks the "Export CSV", "Export PDF", or "Export Excel" button.
2. The **System** calculates the total number of records matching the active filter criteria.
3. If the record count is within the export limit (`<= 20,000` rows per `export_max_rows` setting):
   - The **System** streams or compiles the file containing all matching rows.
   - The exported document includes standard metadata headers: `Generated by` (Admin full name), `Generated at` (ISO timestamp), `Active filters` applied, and the total record count.
   - For PDF documents, the system embeds Unicode fonts that fully support Vietnamese diacritics.
4. The browser triggers the file download to the Librarian's local machine.
5. The flow resumes at Step 4 of the Basic Flow.

#### 2.2.5 Export Refused Due to Size Threshold

_Branching point: At Step 2 of Alternative Flow 2.2.4, if the query results exceed the system export ceiling._

1. The **System** detects that the matching row count exceeds `export_max_rows` (20,000 rows).
2. The **System** halts file generation and displays an alert dialog: _"Export query exceeds the maximum limit of 20,000 records. Please refine your date range or filter criteria before exporting."_
3. The **Librarian (Admin)** narrows the date range or selects a specific category filter.
4. The flow resumes at Step 3 of Alternative Flow 2.2.4.

#### 2.2.6 No Records Match Search or Filter Criteria

_Branching point: At Step 3 of the Basic Flow or Step 2 of Alternative Flow 2.2.1, if no transactions match the query._

1. The **System** displays an empty state placeholder: _"No inventory transactions match the selected filters."_
2. The **System** provides a "Reset Filters" action button.
3. The **Librarian (Admin)** clicks "Reset Filters" to return to the default log view.
4. The flow resumes at Step 3 of the Basic Flow.

## 3. Special Requirements

### 3.1 Audit Log Immutability

- Inventory transactions are append-only. The database schema must enforce through PostgreSQL Row-Level Security (RLS) and table rules that `UPDATE` and `DELETE` operations on `inventory_transactions` are strictly prohibited (`FR-INV-05`, `FR-SYS-03`).
- For any book, the algebraic sum of historical `delta` values across its inventory transactions must mathematically equal its current non-retired copy count.

### 3.2 Performance and Pagination

- Query responses for the paginated log table must return in under 1.0 second for standard views (`NFR-04`), supported by composite indexes on `(book_id, created_at)` and `(type, created_at)`.
- Client-side pagination must default to 50 items per page with server-side limit and offset cursor evaluation.

### 3.3 Security and Access Control

- Access to the `/admin/inventory-history` endpoint and underlying RPCs is restricted exclusively to authenticated users possessing the `admin` role (`FR-AUTH-05`). Unauthenticated or student requests must be rejected with HTTP 403 Forbidden.

### 3.4 Internationalization and Font Embedding

- Generated PDF reports must bundle TrueType/OpenType Vietnamese fonts to ensure correct rendering of accented characters and book titles.

## 4. Preconditions

### 4.1 Staff Authentication and Authorization

The Librarian is signed in to an active session with verified `admin` role privileges.

### 4.2 Database Operational State

The Supabase PostgreSQL database and backend storage services are online, and the `inventory_transactions` table is accessible.

## 5. Postconditions

### 5.1 Audit Log Inspected and Unchanged

- The Librarian has reviewed the historical transactions.
- No existing records in `inventory_transactions` are modified, deleted, or reordered as a result of viewing or filtering.

### 5.2 Export Artifact Dispatched

- If an export was requested, an export file (CSV, PDF, or XLSX) is produced and delivered to the client with generator metadata and active filter headers.
