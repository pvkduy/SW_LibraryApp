## 1. Use-Case Name

**UC-02 - Sign in and sign out** (Traces to: `FEAT-01`)

### 1.1 Brief Description

This use case enables an authenticated user—either a Student (Reader) or a Librarian (Admin)—to start or end an authenticated session in the ShelfHelp web application. Upon sign-in, the system verifies the user's credentials via the authentication service, checks the user's account status and role (`app_metadata.role`), and routes the user to either the mobile-first Reader Mode or the desktop-first Admin Mode. Upon sign-out, the system revokes the session token and returns the user to the public sign-in view.

### 1.2 Actors

- **Primary Actors:** Student (Reader), Librarian (Admin)
- **Supporting Actor:** Authentication and Email Service (Supabase Auth)

---

## 2. Flow of Events

### 2.1 Basic Flow

This use case starts when an unauthenticated **User** (Student or Librarian) navigates to the ShelfHelp application to start an authenticated session.

1. The **User** selects the "Sign In" option on the navigation bar or landing page.
2. The **System** displays the Sign-In form requesting `Email` and `Password`, along with a "Sign In" button and navigation links to "Register" (`UC-01`) and "Forgot Password" (`UC-03`).
3. The **User** enters their `Email` and `Password` and clicks the "Sign In" button.
4. The **System** validates the input format and transmits the credentials to the **Authentication and Email Service** (Supabase Auth).
5. The **Authentication and Email Service** verifies the credentials and returns an encrypted session token (JWT) containing `app_metadata.role`.
6. The **System** fetches the caller's record from the `profiles` table to verify `profiles.status`.
7. The **System** initializes the authenticated client session and routes the **User** according to their role:
   - If `role = student`: The **System** loads the Reader Mode interface (Catalog / Home dashboard).
   - If `role = librarian` (or `admin`): The **System** loads the Admin Mode interface (Circulation & Inventory dashboard).
8. The use case ends with an active authenticated session.

### 2.2 Alternative Flows

#### 2.2.1 Sign Out of an Active Session

_Branching point: Occurs at any time after Step 7 of the Basic Flow while the User has an active session._

1. The **User** clicks the "Sign Out" (or "Logout") button in the account menu or navigation header.
2. The **System** calls the **Authentication and Email Service** to invalidate the current refresh and access tokens and clears local session state and cached user data.
3. The **System** redirects the **User** to the Sign-In screen and displays a confirmation message. The use case ends.

#### 2.2.2 Invalid Email or Password

_Branching point: At Step 5 of the Basic Flow, if the email does not exist or the password does not match._

1. The **Authentication and Email Service** rejects the authentication attempt.
2. The **System** clears the `Password` field and displays a generic error message: _"Invalid email or password. Please try again."_ (avoiding account enumeration).
3. The **User** may re-enter their credentials (resuming at Step 3 of the Basic Flow) or select "Forgot Password" (`UC-03`).

#### 2.2.3 Unverified Student Email

_Branching point: At Step 5 of the Basic Flow, if the Student's email address has not yet been verified._

1. The **System** blocks session creation and displays a notice: _"Your email address is not yet verified. Please check your university inbox for the activation link."_
2. The **System** displays a "Resend Verification Email" button.
3. If the **User** clicks "Resend Verification Email", the **System** requests a new verification email from the **Authentication and Email Service**. The use case ends.

#### 2.2.4 Restricted or Deactivated Account

_Branching point: At Step 6 of the Basic Flow, when inspecting `profiles.status`._

1. **If `profiles.status = deactivated` (or suspended):**
   - The **System** immediately terminates the session (`ACCOUNT_NOT_ACTIVE`), displays an error message instructing the user to contact the library service desk, and returns to Step 2 of the Basic Flow.
2. **If `profiles.status = restricted` (due to chronic overdue/lost book or unpaid debt):**
   - The **System** allows the **Student** to sign into Reader Mode so they can view their loans, charges, and receipts (`UC-11`, `UC-13`, `UC-18`), but displays a prominent restriction banner and disables checkout and reservation actions.

#### 2.2.5 Session Expiration

_Branching point: During an active session, if both the access token and refresh token expire._

1. The **System** detects an unauthorized/expired token response on the next protected route or Edge Function call.
2. The **System** clears the local session state, redirects the **User** to the Sign-In screen with a notice _"Your session has expired. Please sign in again"_, and resumes at Step 2 of the Basic Flow.

## 3. Special Requirements

### 3.1 Role-Based Access Control (RBAC)

- Role separation between `student` and `librarian`/`admin` must be enforced across four layers: frontend route guards, PostgreSQL Row-Level Security (RLS) policies, Supabase Edge Function checks, and Storage policies (`FR-AUTH-05`, Constitution Principle II).
- A Student attempting to access an Admin route or invoke an Admin Edge Function must be denied with `FORBIDDEN_ROLE` (HTTP 403).

### 3.2 Performance

- Sign-in and sign-out operations must complete with an average API response time of no more than 800 ms under normal operating conditions.

### 3.3 Security and Session Management

- All authentication requests must be transmitted over HTTPS, using secure password hashing, short-lived JWT access tokens, and automatic session refresh mechanisms.
- Every Edge Function must re-verify `profiles.status` on the server so a newly deactivated account is blocked immediately even if an older JWT has not yet expired.

---

## 4. Preconditions

### 4.1 System and Network Availability

The ShelfHelp web application, PostgreSQL database, and Supabase Auth service are online and accessible.

### 4.2 Existing User Account

For sign-in, the User possesses a registered Student account (created via `UC-01`) or a pre-provisioned Librarian/Admin account. For sign-out, the User has an active authenticated session.

---

## 5. Postconditions

### 5.1 Successful Sign-In

- An encrypted session is active, and the User is routed to the appropriate interface (`Reader Mode` or `Admin Mode`) with permissions matching `app_metadata.role` and `profiles.status`.

### 5.2 Successful Sign-Out

- The session token is revoked, cached private data is cleared from the browser, and protected routes are no longer accessible without re-authenticating.

### 5.3 Failed Sign-In

- No authenticated session is established, and the User remains in an unauthenticated state.
