## 1. Use-Case Name

**UC-19 - Maintain catalog and copies** (Traces to: `FEAT-05`, `FEAT-22`, `FR-INV-01`, `FR-INV-02`, `FR-INV-03`, `FR-INV-04`, `FR-INV-07`, `FR-INV-09`)

### 1.1 Brief Description

This use case allows a **Librarian (Admin)** to maintain the bibliographic catalog and manage physical inventory items (copies). The Librarian registers titles (manual, ISBN lookup, or bulk CSV), updates metadata, generates barcode labels, adds copies, and adjusts copy statuses. A copy's status is changed in the Books → Copies detail pane: clicking a copy row opens a pane where the admin picks a different status (`available`, `damaged`, `under_repair`, or resolves a `lost` copy to `found`) with a mandatory reason. Bulk CSV import previews the erroneous rows and ingests valid rows in the background.

### 1.2 Actors

- **Primary Actor:** Librarian (Admin)
- **Supporting Actor:** External Bibliographic Lookup Service (Google Books API / Open Library API), Supabase Storage (Book Covers Bucket)

## 2. Flow of Events

### 2.1 Basic Flow

This use case begins when an authenticated **Librarian (Admin)** accesses the ShelfHelp Administration Portal to add a new book title and register its physical copies.

1. The **Librarian** navigates to the "Catalog & Inventory" management section (`/admin/books`) and clicks the "Add New Book" button.
2. The **System** presents the Book Registration interface offering three creation modes:
   - Automated ISBN Lookup
   - Manual Metadata Entry
   - Bulk CSV Import
3. The **Librarian** selects "Automated ISBN Lookup", enters the 10- or 13-digit ISBN barcode string, and triggers "Lookup Metadata".
4. The **System** invokes the external bibliographic lookup service (`lookupIsbn` via Google Books API with fallback to Open Library), retrieves bibliographic information, and automatically populates the form fields: `Title`, `Authors`, `Publisher`, `Publication Year`, `Language`, `Category`, `Field of Study`, `Description`, `Keywords`, and preview cover image URL.
5. The **Librarian** reviews the autofilled fields, refines or enriches metadata, specifies the `Default Shelf Location` (e.g., `A3-204`), assigns the `Collection Tier` (`Standard` or `Premium`), sets the `Replacement Price` (VND), and uploads a high-resolution cover image to the `covers` storage bucket if needed.
6. The **Librarian** enters the initial number of physical copies to add (e.g., 3 copies), specifies individual copy condition (`good`) and acquisition source (`manual_addition: purchase_outside_batch`), and clicks "Save and Create Copies".
7. The **System** executes a server-side PostgreSQL transaction that:
   - Validates that the ISBN is unique across all existing catalog books.
   - Inserts the new `books` record with initial denormalized counters (`total_copies = 3`, `available_copies = 3`, `queue_length = 0`, `popularity_score = 0`).
   - Generates unique Code 128 barcodes for each new copy (e.g., `CP-BK00123-01`, `CP-BK00123-02`, `CP-BK00123-03`) and inserts records into the `copies` table with status `available`.
   - Records an immutable `inventory_transactions` record for each copy with `type = manual_addition`, `delta = +1`, `operator_id = librarian.id`, and `reason = "Initial catalog registration"`.
   - Enqueues an asynchronous re-embedding task to update the vector embedding and full-text search index for the AI Assistant and discovery engine.
8. The **System** displays a success notification with the newly registered book details, lists the generated copy barcodes, and offers an immediate option to print barcode labels. The use case ends.

### 2.2 Alternative Flows

#### 2.2.1 Auto-fill Metadata via External ISBN Lookup Failure or Timeout

_Branching point: At Step 4 of the Basic Flow, if the external ISBN lookup service returns no result, encounters a network timeout, or returns a 404 response._

1. The **System** displays a warning notification: _"No metadata found for ISBN. Please enter book details manually."_
2. The **System** retains the typed ISBN in the form without losing input data and enables all manual input fields.
3. The **Librarian** manually inputs the book metadata (`Title`, `Authors`, `Publisher`, `Year`, `Category`, `Description`, `Shelf Location`, `Replacement Price`).
4. The flow resumes at Step 6 of the Basic Flow.

#### 2.2.2 Duplicate ISBN Handling and Copy Top-Up

_Branching point: At Step 4 or Step 7 of the Basic Flow, if the entered ISBN already exists in the catalog database._

1. The **System** flags a duplicate ISBN conflict and presents the existing book record with title, author, and current copy count.
2. The **System** displays a prompt: _"This title is already registered in the catalog. Would you like to add new copies to the existing record instead?"_
3. If the **Librarian** confirms:
   - The **System** switches to the "Add Copies to Existing Title" form.
   - The **Librarian** enters the quantity of additional copies, condition, and shelf location overrides.
   - The **System** creates the new copy records, assigns new Code 128 barcodes, appends `manual_addition` inventory transactions, increments `total_copies` and `available_copies`, and checks for waiting reservations via [Extension Point 6.1](#61-automatic-reservation-promotion-on-new-available-copy).
   - The use case ends.
4. If the **Librarian** cancels, the **Librarian** corrects the ISBN string or abandons the operation, and the flow resumes at Step 3 of the Basic Flow.

#### 2.2.3 Bulk CSV Catalog Import with Partial Validation Errors

_Branching point: At Step 3 of the Basic Flow, if the Librarian chooses "Bulk CSV Import"._ 

1. The **Librarian** selects "Bulk CSV Import" and uploads a UTF-8 `.csv` file (max 2 MB, up to 1,000 rows) matching the standard template.
2. The **System** validates every row. If any rows are erroneous, the **System** shows a preview of **only the erroneous rows** with per-row reasons.
3. Valid rows are ingested in the background (the ingestion is underlying logic, not a UI step). The use case ends.

#### 2.2.4 Manual Copy Status Adjustment and Audit Logging

_Branching point: An authenticated Librarian needs to inspect or change the status of an existing copy from the inventory table._

1. The **Librarian** opens the Books → Copies tab and clicks a copy row.
2. The **System** opens the detail pane showing the copy's current status (`available`, `damaged`, `under_repair`, or `lost`), shelf location, and history.
3. The **Librarian** picks a different operational status (`damaged`, `under_repair`, `available`, or `found` to resolve a `lost` copy) and enters a mandatory reason.
   - _Constraint:_ The system disables transitions to `borrowed` or `held` (checkout/promotion only) and prevents changing a `held` copy to `lost` without releasing the hold.
4. The **Librarian** confirms.
5. The **System** updates the copy status, recalculates `available_copies`, and inserts an immutable `inventory_transactions` record (`type = status_change` or `found`).
6. If the copy transitioned to `available`, the **System** triggers reservation promotion via [Extension Point 6.1](#61-automatic-reservation-promotion-on-new-available-copy). The use case ends.

#### 2.2.5 Copy Barcode Label Sheet Export and Printing

_Branching point: The Librarian needs to print physical barcode labels for newly created or damaged-label copies._

1. From the book copy list or bulk copy management view, the **Librarian** selects one or more physical copy checkboxes.
2. The **Librarian** clicks "Print Barcode Labels".
3. The **System** compiles the selected copy records (Title, Call Number/Shelf Location, Code 128 barcode representation, Copy Barcode ID, University of Science Library branding) and renders a print-ready PDF formatted for standard Avery/thermal label sheets.
4. The **Librarian** downloads or sends the PDF to the library thermal/laser label printer. The use case ends.

## 3. Special Requirements

### 3.1 Security and Role-Based Authorization

- Access to catalog modification and copy creation endpoints is strictly restricted to authenticated users holding the `admin` (`librarian`) role verified via Supabase JWT claims and server-side PostgreSQL RLS policies (`FR-AUTH-05`).
- Any attempt by a `student` or anonymous user to submit catalog mutations is rejected with an HTTP 403 Forbidden.

### 3.2 Data Integrity and Concurrency

- Catalog books and physical copies are never hard-deleted from the database to preserve historical borrowing integrity and audit trails (`POL-13`). Retired items are decommissioned via Write-Off Slips (`UC-22`).
- Each copy addition or status transition must write an immutable row to `inventory_transactions` with foreign key references, user attribution, and timestamp (`FR-INV-05`).
- Denormalized counters on `books` (`total_copies`, `available_copies`) must be updated within the same database transaction via ACID triggers, with nightly cron reconciliation (`FR-INV-09`, `FR-SYS-02`).

### 3.3 Search Vector and AI Re-embedding Pipeline

- Any modification to embedded fields (`title`, `authors`, `description`, `keywords`, `category`) automatically marks the book for background re-embedding in `book_embeddings` via pgvector and the AI assistant embedding pipeline (`FR-INV-03`, `FR-AI-01`). Shelf location or price edits alone do not trigger re-embedding.

### 3.4 Performance and Usability

- Automated ISBN lookup must return responses within 2.0 seconds under stable external network conditions, with graceful client timeout fallback after 4.0 seconds.
- Bulk CSV imports of up to 1,000 items must complete within 10 seconds through chunked database execution.

## 4. Preconditions

### 4.1 Staff Authentication

The Librarian is logged into the ShelfHelp management portal with an active session holding valid `admin` role privileges.

### 4.2 System and Storage Availability

The ShelfHelp PostgreSQL database and Supabase Storage bucket (`covers`) are operational and accessible.

---

## 5. Postconditions

### 5.1 Catalog and Copy Persisted

- The new book record is saved in the `books` table with updated search vectors.
- Physical copies are created in the `copies` table with unique Code 128 barcodes and initial status `available`.
- Audit records are appended to `inventory_transactions`.
- If copies become `available` for a title with active reservation queues, eligible reservations are promoted.

### 5.2 Catalog Operation Aborted

- If validation fails or the Librarian aborts prior to confirmation, no database records or storage assets are committed.

## 6. Extension Points

### 6.1 Automatic Reservation Promotion on New Available Copy

- **Location:** Step 7 of Basic Flow, or Step 3 of Alternative Flow 2.2.2, or Step 6 of Alternative Flow 2.2.4.
- **Trigger:** When a physical copy becomes `available` and the book has an active reservation queue (`queue_length > 0`).
- **Behavior:** The system invokes the automated reservation promotion engine (`FR-RES-02`), assigning the copy to the first eligible student in queue, transitioning copy status to `held`, setting reservation to `ready_for_pickup`, generating a 48-hour pickup window and pickup code, and dispatching notification emails.
