## 1. Use-Case Name

**UC-25 - Receive an acquisition shipment** (Traces to: `FEAT-20`, `FEAT-22`, `FR-SUGG-07`, `FR-SUGG-08`, `FR-SUGG-09`, `FR-INV-04`, `FR-INV-05`, `FR-RES-02`, `POL-12`)

### 1.1 Brief Description

This use case enables a **Librarian (Admin)** to process incoming physical book shipments delivered against an ordered acquisition batch. The Librarian inspects delivered parcels, verifies received quantities against purchase order batch lines, forces bibliographic catalog record creation for newly acquired titles if not already present, generates unique physical copy barcodes (Code 128), and logs individual shipment receipts (supporting full, partial, or over-receipt deliveries). Upon recording a receipt, the system registers new physical copies with status `available`, creates immutable `batch_receipt` inventory transactions, triggers reservation queue promotion if waiting student requests exist, notifies original student requesters that their requested title has arrived, and supports final batch closure.

### 1.2 Actors

- **Primary Actor:** Librarian (Admin)
- **Supporting Actor:** Book Vendor / Courier (External physical delivery agent), Notification Service

## 2. Flow of Events

### 2.1 Basic Flow

This use case begins when physical parcels containing ordered books arrive at the library receiving dock and an authenticated **Librarian (Admin)** logs the shipment against an existing acquisition batch.

1. The **Librarian** navigates to the Acquisition Batches section at `/admin/batches` and selects the target batch in `ordered` or `receiving` status (e.g., _"Semester 2 - 2026 Textbook Procurement"_).
2. The **System** presents the Batch Detail screen (`/admin/batches/:id`) displaying batch status, vendor, activity log, and the list of line items showing: ISBN, Title, Author, Ordered Quantity, Previously Received Quantity, and Line Status (`pending`, `partial`, `received`).
3. The **Librarian** unpacks the shipment parcel and locates the batch line matching the delivered title.
4. The **Librarian** clicks "Receive Copies" on the target batch line.
5. The **System** checks whether the book title already exists in the library catalog:
   - The book is found in the catalog with an existing `books` record.
6. The **System** opens the Receiving Modal prefilled with the remaining pending quantity (e.g., Ordered: 5, Received: 0, Pending: 5).
7. The **Librarian** counts the physical books received, inputs the quantity received (e.g., 5 copies), selects the physical condition (`good`), designates the target shelf location (or confirms book default), enters the delivery note / vendor invoice number, and clicks "Confirm Receipt".
8. The **System** executes an atomic server-side transaction that:
   - Transitions the batch line status to `received` (quantity received = quantity ordered).
   - If the batch was previously `ordered`, updates batch status to `receiving` (or `closed` if all lines are satisfied).
   - Creates 5 new physical copy records in the `copies` table with status `available`, linked to the batch via `acquisition_source = batch` and assigned unique Code 128 barcodes (e.g., `CP-2026-9041` to `CP-2026-9045`).
   - Inserts 5 immutable `inventory_transactions` rows with `type = batch_receipt`, `delta = +1`, `reference_id = batch.id`, and `reason = "Acquisition shipment receipt"`.
   - Increments the book's denormalized counters (`total_copies = total_copies + 5`, `available_copies = available_copies + 5`).
   - Updates linked student suggestions to status `received`.
   - Appends a detailed entry to the batch activity log recording the operator, timestamp, line title, and quantity received.
   - Triggers reservation queue promotion via [Extension Point 6.1](#61-automatic-reservation-promotion-on-new-physical-copies) if waiting holds exist.
9. The **System** dispatches notification emails and in-app alerts to all students whose suggestions were satisfied by this shipment, announcing that the book is now available in the library collection (`FR-SUGG-09`).
10. The **System** displays a success message, updates the batch receiving progress bar to 100%, and displays a button to print barcode label sheets. The use case ends.

### 2.2 Alternative Flows

#### 2.2.1 Receiving a Title Not Yet in the Library Catalog

_Branching point: At Step 5 of the Basic Flow, if the delivered book title was suggested and ordered but has no bibliographic record in the catalog `books` table._

1. The **System** detects that the ISBN is not present in the catalog database.
2. The **System** blocks direct copy generation and displays a mandatory prompt (`FR-SUGG-07`):
   - _"This acquired title is not yet cataloged. You must create the bibliographic book record before generating physical copies."_
3. The **Librarian** clicks "Create Catalog Record".
4. The **System** launches the Book Creation dialog, prefilling the title, author, and ISBN from the acquisition batch line.
5. The **Librarian** reviews the metadata, enriches classification fields (publisher, publication year, category, shelf location, replacement price, collection tier), and saves the book.
6. The **System** creates the new `books` record.
7. The flow automatically resumes at Step 6 of the Basic Flow to complete receiving copies against the newly created catalog record.

#### 2.2.2 Partial Line Shipment and Staged Receiving

_Branching point: At Step 7 of the Basic Flow, if the vendor delivers only part of the ordered line quantity (e.g., vendor delivers 3 copies out of 5 ordered due to backorder)._

1. The **Librarian** enters the quantity received as `3` (less than ordered quantity `5`).
2. The **Librarian** inputs a receiving note: _"Partial shipment received. 2 copies on vendor backorder."_
3. The **Librarian** clicks "Confirm Receipt".
4. The **System** updates the batch line status to `partial` (Received: 3, Pending: 2).
5. The **System** generates 3 new copy records and 3 `batch_receipt` inventory transactions.
6. The batch status remains `receiving`.
7. When the remaining 2 copies arrive at a later date, the Librarian repeats the flow to receive the remaining quantity, transitioning the line to `received`. The use case ends.

#### 2.2.3 Over-Receipt Handling with Vendor Delivery Discrepancies

_Branching point: At Step 7 of the Basic Flow, if the vendor delivers more copies than originally ordered (e.g., promotional extra copy, ordered 5, delivered 6)._

1. The **Librarian** inputs the actual quantity received as `6` (greater than ordered quantity `5`).
2. The **System** flags an over-receipt warning: _"Received quantity (6) exceeds ordered quantity (5). An explanatory note is mandatory to record excess inventory."_
3. The **Librarian** enters a mandatory note: _"Vendor included 1 complimentary inspection copy."_
4. The **Librarian** confirms receipt.
5. The **System** accepts the over-receipt, sets line status to `received` with quantity 6, creates 6 copy records with barcodes, and logs the discrepancy in the batch activity log. The use case ends.

#### 2.2.4 Batch Closure with Pending Lines Returning to Backlog

_Branching point: The Librarian needs to finalize and close an acquisition batch even though certain lines remain unfulfilled or cancelled by the supplier._

1. The **Librarian** clicks "Close Batch" on a batch in `receiving` status where one or more lines are still `pending` or `partial`.
2. The **System** displays the Batch Closure Confirmation dialog showing a breakdown of all unfulfilled lines (`POL-12`):
   - _"3 line items have unfulfilled quantities totaling 7 copies. Closing this batch will mark unfulfilled lines as 'not_received'."_
   - _"Associated student suggestions for unfulfilled lines will automatically return to the Approved Backlog."_
3. The **Librarian** enters a mandatory closure note (e.g., _"Supplier confirmed out of print; closing batch for semester reconciliation"_) and confirms.
4. The **System** executes a transaction that:
   - Sets the batch status to `closed`.
   - Sets all unfulfilled or remaining partial lines to status `not_received`.
   - Reverts all associated unfulfilled suggestions from `in_batch` back to `approved` in the backlog.
   - Appends the closure event to the batch activity log.
5. The **System** displays the finalized batch summary. The use case ends.

#### 2.2.5 Immediate Barcode Label Printing for Received Shipment

_Branching point: At Step 10 of the Basic Flow, the Librarian wants to print physical spine and barcode labels for all newly received copies._

1. The **Librarian** clicks "Print Labels for This Shipment".
2. The **System** filters all copies created in the current receiving transaction.
3. The **System** renders a formatted PDF document containing Code 128 barcodes, call numbers, book titles, and university library markings configured for standard adhesive label rolls.
4. The **Librarian** prints the labels and affixes them to the physical book spines before placing books on the staging or circulation shelves. The use case ends.

## 3. Special Requirements

### 3.1 Transaction Atomicity and Inventory Provenance

- Creating physical copies, updating line receiving counters, logging inventory transactions, updating denormalized catalog counters, and updating suggestion statuses must occur within a single atomic PostgreSQL transaction (`FR-SUGG-07`).
- Every created copy must link to the originating batch ID in `inventory_transactions` (`type = batch_receipt`) to satisfy university audit and asset acquisition tracking standards (`FR-INV-05`).

### 3.2 No Hard Deletion Policy

- Neither batches, batch lines, nor received copies can ever be deleted. Incomplete orders are closed with lines marked `not_received` (`POL-12`).

### 3.3 Notification Delivery and Idempotency

- When an acquired book is received, all students associated with the suggestion group must be notified once per event (`FR-SUGG-09`).
- If an admin edits receiving notes or processes multiple partial receipts for the same line, duplicate notifications for already-notified students must be prevented (`TS-45`).

### 3.4 Role-Based Access Control

- Only users with verified `admin` (`librarian`) role can access batch receiving workflows or create physical inventory copies (`FR-AUTH-05`).

## 4. Preconditions

### 4.1 Staff Authentication

The Librarian is logged into the administrative portal with an active session holding acquisition and inventory management privileges.

### 4.2 Ordered Batch Existence

An acquisition batch exists in the system with status `ordered` or `receiving`.

---

## 5. Postconditions

### 5.1 Shipment Received and Copies Activated

- Physical copies are created in `copies` table with status `available` and unique Code 128 barcodes.
- Batch line item quantities and statuses (`received` or `partial`) are updated.
- `inventory_transactions` records of type `batch_receipt` are committed.
- Book catalog counters (`total_copies`, `available_copies`) are incremented.
- Suggestion statuses update to `received` and students receive arrival notifications.
- Eligible reservation holds are promoted if queues exist.

### 5.2 Receiving Aborted

- If catalog creation is cancelled or the modal is closed without confirmation, no copies are created and batch lines remain unchanged.

## 6. Extension Points

### 6.1 Automatic Reservation Promotion on New Physical Copies

- **Location:** Step 8 of Basic Flow.
- **Trigger:** When newly received copies transition to `available` and the book title has waiting reservations (`queue_length > 0`).
- **Behavior:** The system invokes the automated reservation promotion engine (`FR-RES-02`), allocating available copies to waiting students in queue priority order, setting reservations to `ready_for_pickup`, copy statuses to `held`, setting 48-hour pickup deadlines, and sending pickup notifications.
