## 1. Use-Case Name

**UC-03 - Recover account credentials** (Traces to: `FEAT-01`)

### 1.1 Brief Description

This use case enables a Student (Reader) who has forgotten their password to securely regain access to their ShelfHelp account without requiring manual intervention from library staff. The student requests a password reset by providing their registered institutional email address, receives a time-limited recovery link via the external authentication and email service, and sets a new compliant password.

### 1.2 Actors

- **Primary Actor:** Student (Reader)
- **Supporting Actor:** Authentication and Email Service (Supabase Auth & SMTP/Email API)

---

## 2. Flow of Events

### 2.1 Basic Flow

This use case begins when an unauthenticated **Student** realizes they cannot recall their password and navigates to the Sign-In screen.

1. The **Student** clicks the "Forgot Password?" link on the Sign-In screen.
2. The **System** displays the Password Recovery Request form containing an input field for `Institutional Email`, a "Send Reset Link" submit button, and a "Back to Sign In" link.
3. The **Student** enters their registered `Institutional Email` and clicks the "Send Reset Link" button.
4. The **System** validates the email syntax and forwards the password reset request to the **Authentication and Email Service** (Supabase Auth).
5. The **Authentication and Email Service** verifies that an active account matches the email address, generates a single-use, time-limited cryptographically signed recovery token, and sends an email containing the password reset URL to the **Student**'s inbox.
6. The **System** displays a confirmation message: _"If an account matches that email address, we have sent a password reset link. Please check your university inbox."_
7. The **Student** opens the recovery email and clicks the password reset link.
8. The **System** verifies the recovery token with the **Authentication and Email Service** and displays the "Set New Password" form containing `New Password` and `Confirm New Password` fields.
9. The **Student** enters a compliant `New Password`, repeats it in `Confirm New Password`, and clicks the "Update Password" button.
10. The **System** validates that the password satisfies complexity rules and that both fields match, then instructs the **Authentication and Email Service** to update the stored password hash and invalidate the recovery token.
11. The **System** displays a success notification (_"Your password has been updated successfully"_) and redirects the **Student** to the Sign-In screen (`UC-02`). The use case ends.

### 2.2 Alternative Flows

#### 2.2.1 Invalid Email Format

_Branching point: At Step 4 of the Basic Flow, if the entered string is not a valid email format._

1. The **System** prevents form submission and highlights the `Institutional Email` input field.
2. The **System** displays an inline validation error: _"Please enter a valid institutional email address."_
3. The **Student** corrects the email address and resubmits.
4. The flow resumes at Step 4 of the Basic Flow.

#### 2.2.2 Unregistered or Deactivated Email Address

_Branching point: At Step 5 of the Basic Flow, if the submitted email does not match any existing account or belongs to a deactivated account._

1. The **Authentication and Email Service** does not generate a token and sends no email.
2. To prevent account enumeration, the **System** still displays the identical generic confirmation message from Step 6 of the Basic Flow (_"If an account matches that email address, we have sent a password reset link..."_).
3. The use case ends without modifying any account records.

#### 2.2.3 Expired or Already-Used Recovery Link

_Branching point: At Step 8 of the Basic Flow, if the Student clicks a reset link whose token has expired or has already been consumed._

1. The **Authentication and Email Service** rejects the token validation check.
2. The **System** displays an error screen: _"This password reset link is invalid or has expired."_ alongside a "Request a New Reset Link" button.
3. The **Student** clicks "Request a New Reset Link", and the flow returns to Step 2 of the Basic Flow.

#### 2.2.4 Weak Password or Confirmation Mismatch

_Branching point: At Step 10 of the Basic Flow, if the `New Password` fails minimum security requirements or does not match `Confirm New Password`._

1. The **System** highlights the invalid password field(s) and displays a specific validation message describing the unmet requirement.
2. The **System** clears both password inputs.
3. The **Student** enters a valid password and confirmation.
4. The flow resumes at Step 9 of the Basic Flow.

#### 2.2.5 Rate Limit Exceeded on Recovery Requests

_Branching point: At Step 4 of the Basic Flow, if the Student submits repeated recovery requests within the cooldown window._

1. The **System** blocks the request and returns a rate-limit warning: _"Too many recovery attempts. Please wait a few minutes before requesting another link."_
2. The **Student** waits for the cooldown timer to expire before retrying or checks their inbox for the previously dispatched email (resuming at Step 7 of the Basic Flow).

## 3. Special Requirements

### 3.1 Security and Anti-Enumeration

- Recovery responses at Step 6 must be indistinguishable between registered and unregistered email addresses so attackers cannot probe which student emails exist in the database.
- Recovery tokens must be single-use, cryptographically random, transmitted exclusively over HTTPS, and expire automatically after a configured duration (e.g., 60 minutes).
- Updating the password must revoke any other active refresh tokens/sessions associated with the account.

### 3.2 Performance

- The initial recovery request submission (Steps 3–6) and the password update transaction (Steps 9–11) must each complete within 800 ms of server processing time under normal conditions.

### 3.3 Accessibility and Usability

- Both the "Password Recovery Request" and "Set New Password" forms must comply with WCAG 2.1 Level AA standards, including keyboard navigation, focus management on error states, and clear password visibility toggles.

---

## 4. Preconditions

### 4.1 System and External Service Availability

The ShelfHelp web application, PostgreSQL database, and external Authentication and Email Service (Supabase Auth and SMTP provider) are operational and reachable.

### 4.2 Access to Registered Email Inbox

The Student has an existing registered account in ShelfHelp (`UC-01`) and has access to their university email inbox to retrieve the recovery link.

---

## 5. Postconditions

### 5.1 Password Successfully Reset

- The Student's password hash in Supabase Auth is updated to the new credential.
- The recovery token is consumed and cannot be reused.
- Prior active sessions for that user are invalidated, and the Student can sign in (`UC-02`) using the new password.

### 5.2 Recovery Uncompleted or Aborted

- If the Student does not click the emailed link or abandons the flow prior to Step 10, the existing password hash and account state remain unchanged.
