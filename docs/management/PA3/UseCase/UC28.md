## 1. Use-Case Name

**UC-28 - View notifications** (Traces to: `FR-NOTIF-01`, `TS-43`)

### 1.1 Brief Description

This use case allows an authenticated User (Student Reader or Librarian) to access their Notification Center, review alerts, track unread counts via a live bell badge, and manage read states individually or in bulk. Notifications announce a feature/event, and the center offers mark-read (single and "mark all") and All/Unread read-status filters.

### 1.2 Actors

- **Primary Actor:** Student (Reader) or Librarian (Admin)
- **Supporting Actor:** Notification Service & Supabase Realtime Engine

---

## 2. Flow of Events

### 2.1 Basic Flow

This use case begins when an authenticated **User** clicks the notification bell icon in the main application header or navigates directly to the Notification Center (`/notifications`).

1. The **User** clicks on the notification bell icon located in the navigation header bar.
2. The **System** opens the notification dropdown preview displaying the top 5 most recent notifications and a badge displaying the count of unread items.
3. The **User** clicks "View all notifications" to open the full Notification Center (`/notifications`).
4. The **System** queries the user's records in the `notifications` table, ordering them newest first (paginated at 30 items per page).
5. The **System** displays the notification list:
   - Each notification shows an icon indicating its category (e.g., Loan Due, Pickup Ready, Reservation Promoted, Membership Expiry), subject title, timestamp (relative time, e.g., "10 minutes ago"), message preview, and an unread indicator dot for unread messages.
   - An action bar with "Mark all as read" and status filters ("All", "Unread").
6. The **User** clicks on an unread notification to inspect its details.
7. The **System** updates the notification record in the database, setting `read_at = NOW()` and `is_read = true`.
8. The **System** removes the unread emphasis from the notification item and automatically decrements the unread count displayed on the header bell badge by 1.
9. The **User** finishes reviewing their notifications and closes the page. The use case ends.

### 2.2 Alternative Flows

#### 2.2.1 Real-Time Notification Delivery While In-App

_Branching point: While the User is actively navigating any screen within the ShelfHelp application._

1. A background event occurs (e.g., an automated nightly due-date scan `FR-NOTIF-02`, a reservation promotion `FR-RES-02`, or an admin manual reminder `FR-NOTIF-04`) that inserts a new row into the `notifications` table for the user.
2. The **Supabase Realtime Engine** pushes a WebSocket change payload to the client's active listener.
3. The **System** dynamically increments the unread badge count on the header bell icon without requiring a page refresh.
4. If configured in user preferences, the **System** renders a brief toast banner at the top of the viewport showing the notification title.
5. The flow resumes at Step 1 of the Basic Flow when the User chooses to review the notification.

#### 2.2.2 Inspect a Notification

_Branching point: At Step 6 of the Basic Flow._

1. Clicking a notification marks it read (single read); the unread badge decrements.

#### 2.2.3 Mark All Notifications as Read

_Branching point: At Step 5 of the Basic Flow, if the User chooses to clear all pending unread markers._

1. The **User** clicks the "Mark all as read" button on the Notification Center toolbar.
2. The **System** executes an atomic update via the backend API setting `read_at = NOW()` and `is_read = true` for all unread notifications belonging to the authenticated user.
3. The **System** refreshes the displayed list, clearing unread highlighting across all rows.
4. The **System** sets the unread badge count on the header bell to 0.
5. The **System** displays a confirmation toast: _"All notifications marked as read."_
6. The flow resumes at Step 9 of the Basic Flow.

#### 2.2.4 Filter Notifications by Read Status

_Branching point: At Step 5 of the Basic Flow, if the User filters to inspect unread messages only._

1. The **User** selects the "Unread" tab on the filter bar.
2. The **System** filters the notification list to display only records where `is_read = false`.
3. If no unread notifications exist, the system shows an empty state message: _"You have no unread notifications."_
4. The **User** reviews unread items or toggles back to "All".
5. The flow resumes at Step 6 of the Basic Flow.

#### 2.2.5 Empty Notification Inbox

_Branching point: At Step 4 of the Basic Flow, if the user has received zero notifications._

1. The **System** detects that the user's notification count is 0.
2. The **System** renders the empty state illustration accompanied by the message: _"You are all caught up! No notifications to show."_
3. The **User** navigates away. The use case ends.

## 3. Special Requirements

### 3.1 Real-Time Synchronization

- The client application must subscribe to Supabase Realtime Postgres Changes on the `notifications` table filtered by `user_id = current_user_id()`.
- Unread badge counters must update reactively within 500 ms of event insertion without full document reloads (`FR-NOTIF-01`).

### 3.2 Data Privacy and Isolation (RLS)

- Strict Row-Level Security policies must enforce that users can only select, update, or listen to notification rows where `user_id == auth.uid()`.
- Under no circumstances can a student or staff member view another user's notifications.

### 3.3 Pagination and Retention

- The notification list must implement cursor or offset pagination at 30 items per page to ensure fast load times even for long-standing accounts.
- Notifications older than 180 days may be archived or purged by scheduled system maintenance jobs.

### 3.4 Accessibility and Badging

- The unread badge on the notification bell must include an explicit `aria-label` stating the exact number of unread alerts (e.g., `aria-label="3 unread notifications"`).
- Keyboard navigation must allow navigating between notification cards using the Tab and arrow keys, and pressing Enter or Space must trigger the item's action.

## 4. Preconditions

### 4.1 Authenticated User Session

The User is signed in to the ShelfHelp application with a valid authentication token.

### 4.2 WebSocket Subscription Channel

The client browser has successfully established a WebSocket connection to the real-time notification channel.

---

## 5. Postconditions

### 5.1 Read Status Updated

- Opened notifications are updated with `is_read = true` and the current timestamp in `read_at`.
- The database state reflects the change immediately.

### 5.2 Unread Counter Synced

- The badge counter in the user interface is updated to match the exact count of remaining unread notifications in the database.
