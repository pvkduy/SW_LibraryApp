## 1. Use-Case Name

**UC-23 - Manage receipts and reversals** (Traces to: `FEAT-09`, `FEAT-24`, `FR-RCPT-01`, `FR-RCPT-02`, `FR-RCPT-03`, `FR-RCPT-04`, `FR-RCPT-05`, `FR-RCPT-06`, `FR-MEM-07`, `DEC-09`, `DEC-10`, `DEC-40`, `DEC-41`)

### 1.1 Brief Description

This use case enables a **Librarian (Admin)** to inspect the library's financial audit log, create official manual receipts for exceptional counter payments, and process formal receipt reversals and refunds. Receipts in ShelfHelp are strictly immutable insert-only records created for every financial transaction (membership purchases, checkout fees, fine settlements, damage and loss fees). When an administrative error, student refund, or returned-lost exception occurs, the Librarian can execute a full reversal with a mandatory reason code. A reversal generates an immutable negative-amount reversal receipt, updates the derived status of the original receipt (`Reversed` or `Voided`), resets or waives associated charge balances, and revokes membership entitlements if applicable, guaranteeing net-revenue consistency for institutional accounting.

### 1.2 Actors

- **Primary Actor:** Librarian (Admin)
- **Supporting Actor:** Audit and Reporting System

## 2. Flow of Events

### 2.1 Basic Flow

This use case begins when an authenticated **Librarian (Admin)** inspects a financial receipt in the administrative receipt log to verify its provenance and audit details.

1. The **Librarian** navigates to the Financial Management module at `/admin/receipts`.
2. The **System** presents the Receipt Log table with filtering controls for `Date Range`, `Student ID / Name`, `Transaction Type` (membership, premium fee, overdue fine, damage fee, loss fee, manual), `Payment Method` (VNPAY, MoMo, Counter), and `Status` (`Valid`, `Voided`, `Reversed`).
3. The **Librarian** filters or searches by receipt number (e.g., `RCP-2026-00142`) or student identification.
4. The **System** displays the filtered list of receipts, showing receipt number, student name, signed amount (VND), payment method, transaction type, derived status, creator identity, and timestamp.
5. The **Librarian** clicks on a specific receipt row to view its details.
6. The **System** displays the detailed Receipt View (`/admin/receipts/:id`) containing:
   - Full receipt identifier and creation timestamp (`Asia/Ho_Chi_Minh`).
   - Student identity and contact information.
   - Exact payment breakdown and method.
   - Creator attribution (`student`, `admin` staff name, or `system`).
   - Direct clickable reference link to the originating transaction entity (e.g., Loan Item, Payment record, or Membership purchase).
   - Reversal audit link (if the receipt has been reversed).
   - Derived status badge (`Valid`).
7. The **Librarian** reviews the receipt and optionally clicks "Print Receipt Slip" to render a standardized thermal/A4 printable voucher. The use case ends.

### 2.2 Alternative Flows

#### 2.2.1 Creation of a Manual Financial Receipt

_Branching point: A student settles an exceptional fee at the counter (e.g., replacement binding fee, uncataloged archive charge) that does not originate from an automated checkout flow._

1. From the Receipt Management screen, the **Librarian** clicks "Create Manual Receipt" (`FR-RCPT-04`).
2. The **System** presents the Manual Receipt Form containing input fields for `Student ID / Name`, `Amount (VND)`, `Payment Method` (Cash Counter / Bank Transfer), `Transaction Type` (`replacement_fee`, `damage_fee`, `special_service`), `Mandatory Justification / Reason`, and optional `Loan Reference ID`.
3. The **Librarian** enters the student details, exact amount collected, payment method, transaction category, and a mandatory detailed explanation (minimum 10 characters, e.g., _"Collected replacement binding charge for water-damaged archive monograph"_).
4. The **Librarian** submits the form.
5. The **System** validates that:
   - The selected student exists and is registered.
   - The amount is a positive non-zero integer.
   - The mandatory reason is provided.
6. The **System** executes a database transaction that:
   - Assigns the next sequential annual receipt number (`RCP-2026-XXXXX`).
   - Inserts the new receipt row into `receipts` with `is_manual = true`, `created_by = librarian.id`, and `reason = justification`.
   - Records an entry in the system financial ledger.
7. The **System** displays the newly created receipt with a distinctive `[MANUAL]` audit flag and offers a printable receipt slip. The use case ends.

#### 2.2.2 Receipt Reversal for Cashier Entry Error

_Branching point: The Librarian discovers that a counter payment receipt was entered incorrectly or recorded against the wrong student ID._

1. From the receipt detail view, the **Librarian** clicks the "Reverse Receipt" button (`FR-RCPT-05`).
2. The **System** verifies that the receipt is currently in `Valid` status (has not been previously reversed).
3. The **System** displays the Reversal Confirmation dialog requiring:
   - Selection of formal Reversal Reason Code: `entry_error`, `refund_exception`, `lost_returned`, or `cancellation`.
   - Detailed administrative audit note.
   - For settled charge receipts: an option to either restore the charge to `unpaid` or `waive` it permanently.
4. The **Librarian** selects reason code `entry_error`, inputs an explanatory audit note, and chooses "Restore Charge to Unpaid".
5. The **Librarian** clicks "Confirm Reversal".
6. The **System** executes an atomic server-side transaction that:
   - Generates a new negative-amount reversal receipt (e.g., `-30,000 VND`) linked to the original receipt (`reversal_of_id = original.id`).
   - Sets the reason code `entry_error` on the reversal receipt.
   - Updates the originating charge back to `unpaid` status (re-applying debt hold to the student's profile).
   - If paid online, marks the underlying Payment record as `refunded`.
7. The **System** derives the status of the original receipt as `Voided` (due to reason `entry_error`).
8. The **System** displays a confirmation toast and updates the receipt view showing the linked reversal receipt link. The use case ends.

#### 2.2.3 Reversal of Membership Plan Fee and Immediate Access Revocation

_Branching point: An administrative exception requires refunding a purchased Student Membership plan (e.g., duplicate billing or student withdrawal)._

1. The **Librarian** opens the receipt corresponding to a membership plan purchase (`transaction_type = membership`).
2. The **Librarian** clicks "Reverse Receipt".
3. The **System** warns the Librarian: _"Reversing this receipt will immediately terminate the student's active membership plan. The student will instantly revert to non-member borrowing entitlements. Existing active loans will retain their current due dates."_
4. The **Librarian** selects reason code `refund_exception`, enters the authorized administrative justification, and confirms.
5. The **System** executes an atomic transaction (`FR-MEM-07`):
   - Generates the negative reversal receipt linked to the original membership receipt.
   - Transitions the student's membership status to `terminated`.
   - Recalculates the student's current entitlements (reverting to standard borrowing quota).
   - Retains current due dates for all currently checked-out loans.
6. The **System** sends an automated notification email to the student confirming the refund and membership termination. The use case ends.

#### 2.2.4 Attempted Double Reversal on an Already Reversed Receipt

_Branching point: At Step 1 of Alternative Flow 2.2.2 or 2.2.3, if a Librarian attempts to reverse a receipt that already has a linked reversal._

1. The **System** evaluates the receipt's derived status and identifies that a linked reversal receipt already exists (`reversal_of_id != null`).
2. The **System** disables the "Reverse Receipt" button in the UI.
3. If an API request is received directly, the server rejects it with HTTP 409 Conflict (`RECEIPT_ALREADY_REVERSED`).
4. The **System** displays an informational banner: _"This receipt was already reversed on [Timestamp] via Reversal Receipt [Linked Receipt Number]."_
5. The use case ends without making any database changes.

#### 2.2.5 Exporting Audited Financial Receipt Logs

_Branching point: The Librarian or library accountant requires financial receipts export for university auditing._

1. From `/admin/receipts`, the **Librarian** applies desired filters (e.g., Fiscal Month, All Statuses, All Methods).
2. The **Librarian** clicks the "Export Log" button and selects the format (`CSV`, `Excel`, or `PDF`).
3. The **System** compiles all matching receipts, calculating gross collections, total reversals, and net revenue.
4. The **System** generates and streams the downloadable file containing complete audit columns (`receipt_number`, `created_at`, `student_id`, `amount`, `payment_method`, `type`, `status`, `created_by`, `reversal_ref`, `notes`). The use case ends.

## 3. Special Requirements

### 3.1 Strict Immutability and Security Triggers

- Financial receipts must be strictly insert-only (`FR-RCPT-06`, `DEC-10`, `DEC-40`).
- A PostgreSQL database trigger (`BEFORE UPDATE OR DELETE ON receipts`) raises an uncatchable exception on any attempt to update or delete receipt rows. Neither regular admins, the Supabase service role, nor direct SQL queries can modify existing receipt records.
- Statuses (`Valid`, `Voided`, `Reversed`) are dynamically derived based on the existence and reason code of linked reversal receipts.

### 3.2 Gap-Free Annual Numbering and Concurrency

- Receipt identifiers must follow a strict gap-free sequential annual pattern (e.g., `RCP-2026-00001`, `RCP-2026-00002`).
- Sequential number generation must be serialized via database sequences or advisory locks to prevent gaps or duplicate numbers under concurrent staff transactions.

### 3.3 Net Revenue Financial Consistency

- All financial analytics, accounting metrics, and ledger reports must compute net revenue as the signed mathematical sum of all receipts including negative reversal receipts (`DEC-41`).

### 3.4 Role-Based Access Control

- Only users with verified `admin` role can view receipt logs, create manual receipts, or execute reversals (`FR-AUTH-05`).
- Students can only view their own personal receipts via `UC-11` and have no access to reversal endpoints or other students' financial records.

## 4. Preconditions

### 4.1 Staff Authentication

The Librarian is authenticated with an active session holding administrative and financial management permissions.

### 4.2 Receipt Record Existence

For inspection and reversal flows, the target financial receipt row exists in the PostgreSQL database.

---

## 5. Postconditions

### 5.1 Reversal or Manual Receipt Created

- An immutable new receipt row is inserted into the `receipts` table.
- If a reversal was executed, the linked reversal receipt is persisted, the original receipt status reflects `Reversed` or `Voided`, and related charge/membership states are updated.
- Net revenue balances reflect the transaction.

### 5.2 Receipt Operation Aborted

- If input validation fails or the Librarian cancels the reversal dialog, no rows are inserted and existing statuses remain intact.
