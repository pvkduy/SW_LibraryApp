## 1. Use-Case Name

**UC-10 - Check out books** (Traces to: `FEAT-08`, `FEAT-09`, `POL-04`, `POL-05`, `FR-CART-03`, `FR-CART-04`, `FR-CART-05`, `FR-CART-06`, `FR-CART-07`, `FR-CART-08`, `DEC-07`, `DEC-12`, `DEC-13`, `DEC-14`)

### 1.1 Brief Description

This use case allows an authenticated Student (Reader) to submit the items in their borrowing cart as a confirmed library loan request. The checkout process is atomic and validates student standing, debt hold, entitlement limits, duplicate loans, and real-time physical copy availability. Upon validation, the system claims physical copies, locks their status to `held`, generates a unique 6-digit pickup code, clears the borrowing cart, and establishes a 48-hour pickup window. For free loans (Standard books, or Premium books for active members), items transition immediately to `ready_for_pickup`. For fee-bearing loans (Premium books for non-members), the student selects either online simulated payment (with a 30-minute payment deadline) or over-the-counter payment (with a 48-hour hold deadline).

### 1.2 Actors

- **Primary Actor:** Student (Reader)
- **Supporting Systems:** Supabase PostgreSQL Database (RPC transaction with `SKIP LOCKED`), Payment Provider / Simulator

## 2. Flow of Events

### 2.1 Basic Flow

#### 2.1.1 Free Checkout Path (Standard Books & Member Premium)

This sub-flow begins when an eligible **Student** (e.g., active member borrowing any titles, or non-member borrowing Standard titles) clicks "Proceed to Checkout" on the Cart page (`/cart`).

1. The **Student** reviews their cart items, selected loan durations (7 or 14 days), and confirms that total fees are 0 VND.
2. The **Student** clicks the "Confirm Checkout" button.
3. The **System** invokes the server-side Edge Function / RPC `checkout-cart` with a client-generated idempotency key.
4. The **System** executes an atomic database transaction:
   - Validates that the student account is `active`, not restricted, and has 0 outstanding debt balance.
   - Verifies that adding the cart items does not exceed the student's simultaneous item limit (3 for non-members, snapshot limit up to 7 for members; `DEC-22`).
   - Verifies the student holds no duplicate active loan or pending request for any of the books.
   - For each cart line, selects the lowest-numbered copy in `available` status using `SELECT ... FOR UPDATE SKIP LOCKED`.
   - Updates each selected copy's status to `held` (`DEC-07`).
   - Creates a parent `loan_requests` record with a unique 6-digit alphanumeric pickup code.
   - Creates corresponding `loan_items` records in `ready_for_pickup` status, stamping `pickup_deadline = now() + 48 hours`.
   - Clears the student's `cart_items`.
5. The **System** displays the Request Confirmation screen (`/loans/requests/:requestId`), highlighting:
   - Secret 6-digit pickup code (with copy-to-clipboard button and barcode/QR display).
   - 48-hour pickup countdown timer.
   - Pick-up instructions directing the student to present the pickup code or Student ID at the library circulation desk.
6. The **System** dispatches a pickup confirmation email and in-app notification. The sub-flow ends.

#### 2.1.2 Paid Checkout Path (Non-Member Premium via Online Gateway)

This sub-flow begins when a non-member **Student** checks out one or more Premium collection titles incurring borrowing fees.

1. The **Student** clicks "Proceed to Checkout" on the Cart page (`/cart`).
2. The **System** detects payable lines and prompts the student to select a payment method: "Pay Online" or "Pay at Counter".
3. The **Student** selects "Pay Online" and clicks "Confirm Order & Pay".
4. The **System** executes the `checkout-cart` atomic transaction:
   - Validates student standing, limits, and claims available copies, setting each to `held`.
   - Creates the `loan_requests` record.
   - Creates `loan_items` records with status `awaiting_payment`, stamping `payment_deadline = now() + 30 minutes` and the fixed loan fee.
   - Creates a pending `Payment` record linked to the items.
   - Clears `cart_items`.
5. The **System** redirects the student to the Simulated Payment Gateway page (`/pay/:paymentId`).
6. The **System** displays the payable summary (amount in VND, purpose "Premium Book Borrowing Fee") and a 30-minute countdown timer.
7. The **Student** clicks "Pay Now" (or "Simulate Success").
8. The **Payment Provider / Simulator** processes authorization and signals payment success.
9. The **System** invokes `complete-simulated-payment` to atomically:
   - Mark the `Payment` record as `succeeded`.
   - Generate official immutable financial `Receipt` records for each paid item (`DEC-09`, `FR-CART-06`).
   - Transition the `loan_items` status from `awaiting_payment` to `ready_for_pickup`.
   - Generate the 6-digit pickup code and establish a fresh `pickup_deadline = now() + 48 hours`.
10. The **System** redirects the student to the Request Confirmation screen showing the pickup code and 48-hour pickup window. The sub-flow ends.

### 2.2 Alternative Flows

#### 2.2.1 Stock Contention / Copy Claimed Concurrently

_Branching point: At Step 4 of Sub-flow 2.1.1 or 2.1.2, if another user claims the last available copy of a cart book milliseconds prior to transaction commit._

1. The database transaction detects that one or more cart lines cannot acquire an `available` copy with `SKIP LOCKED`.
2. The **System** rolls back the entire checkout transaction (all-or-nothing policy; `POL-04`, `FR-CART-03`).
3. No copies are held, and the student's `cart_items` are preserved intact.
4. The **System** returns an error response identifying the specific unavailable book(s).
5. The **System** re-renders the cart view, highlighting the depleted title with the badge: _"Stock no longer available."_
6. The **Student** removes the unavailable title and retries checkout. The flow resumes at Step 1 of Basic Flow.

#### 2.2.2 Pay at Counter Selected for Paid Checkout

_Branching point: At Step 3 of Sub-flow 2.1.2, if the student selects "Pay at Counter" instead of paying online._

1. The **Student** selects "Pay at Counter" and clicks "Confirm Order".
2. The **System** executes `checkout-cart`:
   - Holds physical copies (`held`).
   - Creates `loan_items` in status `awaiting_payment` with payment method designated as `counter`.
   - Sets `payment_deadline = now() + 48 hours` (aligning payment with the counter pickup window; `DEC-12`).
   - Generates the 6-digit pickup code.
   - Clears `cart_items`.
3. The **System** displays the Request Confirmation screen stating: _"Status: Awaiting Counter Payment. Please visit the library circulation desk within 48 hours, present your pickup code, and pay [Amount] VND before collecting your books."_ The sub-flow ends.

#### 2.2.3 Online Payment Fails or Times Out

_Branching point: At Step 7 of Sub-flow 2.1.2, if the payment fails, is cancelled, or the 30-minute payment window expires._

1. If payment fails or is rejected:
   - The **System** marks `Payment` as `failed`.
   - The **System** transitions the affected `loan_items` to `payment_failed` (`DEC-13`).
   - The **System** presents a payment failure screen with options: "Retry Online Payment", "Switch to Pay at Counter", or "Cancel Request".
   - If the student retries within the original 30-minute window, the flow returns to Step 6 of Sub-flow 2.1.2.
2. If the 30-minute payment window expires without successful payment:
   - The **System** scheduled job (`check-expired-holds`) transitions the items to `expired`.
   - The held physical copies are released back to `available` (or promoted to waiting reservations per `POL-07`).
   - The request is closed. The use case ends.

#### 2.2.4 Switching Online Payment to Counter Payment

_Branching point: While an item is in `awaiting_payment` or `payment_failed` during an online payment attempt._

1. The **Student** views their pending request and selects "Pay at Counter instead" (`FR-CART-05`).
2. The **System** verifies that the item has not already expired or previously switched.
3. The **System** updates the payment method to `counter`, cancels any pending online payment gateway intent, and extends the deadline to 48 hours from request creation (`DEC-12`).
4. The **System** refreshes the screen with the updated counter payment instructions. The flow ends.

#### 2.2.5 Student Cancels Pickup Request Before Handover

_Branching point: If the student cancels an order while items are in `awaiting_payment`, `payment_failed`, or `ready_for_pickup`._

1. The **Student** opens the Request Detail view (`/loans/requests/:requestId`) and clicks "Cancel Request" (`FR-CART-07`).
2. The **System** displays a confirmation dialog warning that held books will be released.
3. The **Student** confirms cancellation.
4. The **System** executes cancellation logic atomically:
   - Updates `loan_items` status to `cancelled`.
   - Releases held copies (`held -> available`), which immediately triggers the promotion and wishlist check (`POL-07`).
   - If the items were already paid online, the system marks the `Payment` as `refunded` and issues a linked reversal `Receipt` (`DEC-11`, `FR-CART-07`).
5. The **System** displays a cancellation confirmation and toast notification. The use case ends.

## 3. Special Requirements

### 3.1 Atomic Inventory Hold and Row-Level Locking

- Checkout must be completely atomic and all-or-nothing (`POL-04`).
- Physical copy assignment must use explicit row locking (`SELECT id FROM copies WHERE book_id = $1 AND status = 'available' ORDER BY copy_number ASC LIMIT 1 FOR UPDATE SKIP LOCKED`) to eliminate race conditions under high concurrent demand.

### 3.2 Pickup Code Generation and Access Control

- Each loan request must generate a unique, cryptographically random 6-digit alphanumeric pickup code (`FR-CART-08`).
- The pickup code must be visible solely to the student who placed the request and authorized library staff (`RLS` access policies).

### 3.3 Pickup Deadlines and Automated Expiration

- Pickup deadlines are strictly 48 hours from the timestamp the item enters `ready_for_pickup`.
- A background cron job (`expire-held-items`) runs periodically to transition items whose `pickup_deadline < now()` to `expired`, automatically releasing physical copies and executing refunds where applicable.

## 4. Preconditions

### 4.1 Active Authenticated Student Account

The Student is authenticated with an `active` account status and has no outstanding overdue fines or debt holds.

### 4.2 Populated Borrowing Cart

The student has at least one valid item in `cart_items`.

---

## 5. Postconditions

### 5.1 Loan Request Created and Physical Copies Held

- A new `loan_requests` record exists with an assigned 6-digit pickup code.
- New `loan_items` records exist in `ready_for_pickup` (free/paid) or `awaiting_payment` status.
- Selected physical copy records in `copies` are transitioned from `available` to `held`.

### 5.2 Cart Cleared

- All items for the student are deleted from `cart_items`.

### 5.3 Transaction Aborted or Rejected

- In the event of stock contention or payment abortion, physical copy statuses remain unchanged and the cart remains intact.

## 6. Extension Points

### 6.1 Counter Pickup and Book Handover

- Upon arriving at the library counter, the student presents their pickup code to library staff, triggering `UC-20 (Hand over requested books)`.

### 6.2 Direct Charge Payment

- If payment is required at the counter or online, the flow links with `UC-13 (Pay a charge)`.
