## 1. Use-Case Name

**UC-16 - Manage book suggestions** (Traces to: `FEAT-18`, `POL-12`, `FR-SUGG-01`, `FR-SUGG-02`)

### 1.1 Brief Description

This use case allows a Student (Reader) to propose new books for library acquisition when desired titles are absent from the catalog. The student provides book metadata (title, author, ISBN or URL link, and an academic justification between 10 and 500 characters). As the student enters details, the system performs live deduplication against both existing catalog holdings and ongoing suggestion clusters ("N other students have requested this"). Students can track their proposals across a transparent status lifecycle (`submitted`, `under_review`, `approved`, `rejected`, `ordered`, `received`), view detailed librarian decision notes, and withdraw pending requests before they are finalized into acquisition batches.

### 1.2 Actors

- **Primary Actor:** Student (Reader)
- **Supporting Actor:** Librarian (Admin) (reviews and updates suggestion statuses via `UC-24`)

## 2. Flow of Events

### 2.1 Basic Flow (Submitting a New Book Suggestion)

1. The **Student** navigates to the Suggestions page (`/suggestions`) and clicks the "Suggest a Book" button.
2. The **System** verifies that the student currently has fewer than 5 open suggestions (`status IN ('submitted', 'under_review')`).
3. The **System** displays the suggestion form containing:
   - `Title` (required, text)
   - `Author` (required, text)
   - `ISBN` or `Web Link` (at least one is mandatory; validated for EAN-13/10 checksum or valid HTTP/HTTPS URL)
   - `Reason / Academic Value` (mandatory textarea, 10 to 500 characters)
   - Live character counter and suggestion quota indicator (e.g., "Open suggestions: 2/5").
4. As the **Student** types the title or ISBN, the **System** performs debounced live querying:
   - Checks the catalog for existing matching books.
   - Checks open suggestion groups for similar pending requests.
5. In this flow, no matching catalog book or active suggestion group is found.
6. The **Student** completes all required fields and clicks "Submit Suggestion".
7. The **System** validates inputs client-side and server-side:
   - Validates that title and author are populated.
   - Confirms that either a valid ISBN or an HTTP/HTTPS link is provided.
   - Checks that the reason contains between 10 and 500 characters.
8. The **System** creates a new `suggestion_groups` cluster row and inserts a `suggestions` record linked to the group with status `submitted` and timestamps `created_at = NOW()`.
9. The **System** displays a success toast: _"Suggestion submitted successfully! You will be notified when librarians review your request."_
10. The **System** redirects the student to the "My Suggestions" tab showing the new proposal in the tracking timeline. The use case ends.

### 2.2 Alternative Flows

#### 2.2.1 Book Already Exists in Library Catalog

_Branching point: At Step 4 of the Basic Flow, if the entered title or ISBN matches a book already in the catalog (`FR-SUGG-01`)._

1. The **System** identifies that the title or ISBN matches an existing catalog entry (`books.id`).
2. The **System** renders an inline warning panel above the form:
   - Displays the matching book cover, title, author, and current availability status.
   - Message: _"This book is already in the library catalog. You do not need to suggest it."_
   - Provides a direct link to open the book's detail page (`/books/:bookId`).
3. If the book is simply checked out, the student is prompted to reserve or wishlist the title instead.
4. The **Student** clicks the catalog link, abandoning the suggestion form. The use case ends.

#### 2.2.2 Attaching to an Existing Open Suggestion Group

_Branching point: At Step 4 of the Basic Flow, if another student has already suggested this title and it is pending review (`POL-12`, `FR-SUGG-01`)._

1. The **System** identifies an existing `suggestion_groups` cluster matching the title/ISBN.
2. The **System** displays an informative notice: _"3 other students have already suggested this book."_
3. The **System** presents an "Attach My Vote / Support This Request" button.
4. The **Student** clicks "Attach My Vote" and enters their specific academic reason.
5. The **System** links the student's suggestion to the existing `suggestion_group_id` and increments the cluster's requester count.
6. The **System** displays a confirmation: _"You have joined the request group for this book! You will receive updates as its acquisition progresses."_
7. The flow resumes at Step 10 of the Basic Flow.

#### 2.2.3 Maximum Open Suggestion Quota Reached (Limit of 5)

_Branching point: At Step 2 of the Basic Flow, if the student already has 5 active open suggestions._

1. The **System** detects that `COUNT(suggestions)` in statuses `submitted` or `under_review` for this student equals 5 (`POL-12`).
2. The **System** disables the "Suggest a Book" button and renders an inline alert on `/suggestions`: _"You have reached your limit of 5 open suggestions. You can submit new requests once existing ones are reviewed or withdrawn."_
3. The use case ends.

#### 2.2.4 Tracking Status and Reviewing Rejection Rationale

_Branching point: At any time, when the student views `/suggestions` to monitor previous submissions._

1. The **Student** opens `/suggestions` and views their list of submitted books.
2. Each suggestion displays an interactive visual timeline showing current lifecycle status:
   - `submitted` -> `under_review` -> `approved` -> `ordered` -> `received`.
3. If a suggestion was rejected (`status = 'rejected'`), the **System** displays:
   - The rejection badge.
   - The formal rejection reason code (e.g., `budget_limit`, `out_of_print`, `duplicate`, `irrelevant`, or `already_in_catalog`).
   - The librarian's explanatory feedback note.
   - If rejected for `already_in_catalog`, a direct clickable link to the catalog item is provided.
4. The use case ends.

#### 2.2.5 Withdrawing an Eligible Suggestion

_Branching point: At Step 2 of Alternative Flow 2.2.4, if the student decides to retract a pending proposal._

1. The **Student** locates a suggestion with status `submitted` or `under_review`.
2. The **Student** clicks the "Withdraw" button (`FR-SUGG-02`).
3. The **System** prompts for confirmation: _"Are you sure you want to withdraw this suggestion? This will free up one slot in your open suggestion quota."_
4. The **Student** confirms the withdrawal.
5. The **System** updates the suggestion record to `withdrawn`:
   - Decrements the active requester counter on the linked group.
   - If no other requesters remain in the group, archives or removes the empty cluster.
6. The **System** displays a toast confirmation: _"Suggestion withdrawn."_
7. The student's open quota is restored immediately. The use case ends.

#### 2.2.6 Prefilling from AI Assistant or Failed ISBN Scan

_Branching point: At Step 1 of the Basic Flow, if the student is navigated here from the AI Assistant (`UC-17`) or Barcode Scanner (`UC-07`)._

1. When the AI Assistant finds no relevant catalog holdings or the Barcode Scanner decodes an unknown ISBN, the UI provides a "Suggest this book" button.
2. The **Student** clicks the button.
3. The **System** opens the suggestion form with query parameters pre-populating `Title`, `Author`, `ISBN`, and an initial draft of the `Reason` based on the assistant discussion context.
4. The flow resumes at Step 3 of the Basic Flow.

## 3. Special Requirements

### 3.1 Deduplication and Accent-Insensitive Clustering

- Book suggestion grouping must employ Vietnamese accent-insensitive and case-insensitive comparison algorithms (`POL-17`, `POL-12`).
- Variations in typing (e.g., "Kỹ nghệ phần mềm" vs "Ky nghe phan mem") must map to the same recommendation cluster to prevent duplicate acquisition batches.

### 3.2 Validation and Input Integrity

- ISBN inputs must strictly validate checksum rules for 10-digit or 13-digit formats.
- URL links must enforce valid URI schemes (`http://` or `https://`).
- The reason field must enforce a strict boundary between 10 and 500 characters to prevent spam while ensuring sufficient academic justification.

### 3.3 Status Lifecycle Progression

- Suggestions transition strictly through defined states: `submitted` -> `under_review` -> `approved` / `rejected` -> `ordered` -> `received` (or `withdrawn`).
- Rejections require a mandatory reason code and optional staff comments (`FR-SUGG-04`).

## 4. Preconditions

### 4.1 Active Account Profile

The Student is authenticated and possesses an `active` account profile (students under `restricted` status cannot submit suggestions per `POL-02` gating rules).

### 4.2 Open Quota Availability

The Student currently has fewer than 5 suggestions in `submitted` or `under_review` status.

---

## 5. Postconditions

### 5.1 Suggestion Submitted and Grouped

- A new row is inserted into `suggestions` with status `submitted`.
- The record is linked to an existing or newly created `suggestion_groups` cluster.
- The student's open suggestion counter is incremented by 1.
- The item appears on the Admin acquisition review board (`UC-24`).

### 5.2 Suggestion Withdrawn

- The suggestion status transitions to `withdrawn`.
- The student's open suggestion counter is decremented by 1.

---

## 6. Extension Points

### 6.1 Extension to Plan Book Acquisitions (UC-24)

- **Condition:** Suggestions submitted by students become inputs for library collection planning.
- **Location:** Step 8 of Basic Flow. Librarians aggregate approved suggestion clusters into formal acquisition batches in `UC-24 - Plan book acquisitions`.
