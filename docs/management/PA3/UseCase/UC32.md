## 1. Use-Case Name

**UC-32 - Configure library policies and membership plans** (Traces to: `FR-SET-01`, `FR-MEM-09`, `TS-34`, `TS-58`)

### 1.1 Brief Description

This use case enables a Librarian (Admin) to maintain the library's operational policies, circulation parameters, financial fee schedules, and membership plan offerings without modifying system code. Configurable parameters include daily fine rates, grace periods, lost-item conversion thresholds, damage fee percentages, loan limits and durations per tier, pickup expiration windows, reservation strike rules, and AI assistant rate caps. Staff can also create, adjust, or deactivate fixed-duration membership plans. Every modification is strictly validated against schemas, applies prospectively to future transactions (protecting active memberships and loans via immutable snapshots), and generates an immutable historical audit record documenting the operator, timestamp, and before/after values.

### 1.2 Actors

- **Primary Actor:** Librarian (Admin)
- **Supporting Actor:** Settings Service & Configuration History Store (PostgreSQL)

## 2. Flow of Events

### 2.1 Basic Flow

This use case begins when an authenticated **Librarian (Admin)** opens the System Settings page (`/admin/settings`).

1. The **Librarian (Admin)** navigates to "Settings & Policies" in the back-office administration portal.
2. The **System** loads the active configuration from the `settings` table (key `library`) and queries the active membership plans list.
3. The **System** renders the Library Configuration portal organized into functional tabs:
   - **Circulation & Fines:** `fine_per_day` (VND), `fine_grace_days`, `lost_threshold_days` (days until auto-conversion), `default_replacement_price` (VND), `pickup_window_hours` (hours hold remains ready), `due_soon_days` (days before due date to alert).
   - **Membership Plans & Tier Limits:** Non-member privileges (`max_items`, `loan_days_options`, `renewals`, `can_reserve`), Premium book borrow fee (`premium_fee_per_7_days`), and the list of active/inactive Membership Plans (name, duration in days, price in VND, allowed simultaneous items, loan duration options, renewal limits, reservation privileges).
   - **Reservations & Penalties:** `reservation.queue_limit`, `reservation.max_active_per_member`, `reservation.strike_window_days`, `reservation.strikes_before_ban`, and `reservation.ban_days`.
   - **Damage Tiers & Assessments:** `damage_tiers_percent` for minor (default 10%), major (default 30%), and unusable (default 100%) condition write-offs.
   - **System Limits & AI Assistant:** `timezone`, `email_domain_allowlist`, `student_id_pattern`, `export_max_rows`, and `chat.rate_per_hour` / `rate_per_day`.
   - **Settings Audit History:** A chronological log displaying historical modifications (`Changed At`, `Operator`, `Setting Key`, `Previous Value`, `New Value`).
4. The **Librarian (Admin)** selects a configuration category to inspect active settings and their current values.
5. The **Librarian (Admin)** completes review and leaves the settings screen. The use case ends.

### 2.2 Alternative Flows

#### 2.2.1 Modify Circulation Limits and Fine Rates

_Branching point: At Step 4 of the Basic Flow, if the Librarian updates an operational policy parameter._

1. The **Librarian (Admin)** modifies a setting input field (e.g., changes `fine_per_day` from `2,000` to `3,000` VND, or updates `pickup_window_hours` from `48` to `72`).
2. The **System** displays the previously saved value alongside the pending value for immediate comparison.
3. The **Librarian (Admin)** clicks "Save Policy Changes".
4. The **System** validates the input against defined type and range constraints (e.g., fine rate cannot be negative, durations must be positive integers).
5. The **System** executes an atomic update transaction:
   - Updates the target key in the `settings` table (`key = 'library'`).
   - Inserts a record into the `settings_history` audit table recording `changed_by = admin_id`, `changed_at = NOW()`, `setting_key = 'fine_per_day'`, `old_value = 2000`, `new_value = 3000` (`FR-SET-01`, `TS-58`).
6. The **System** displays a confirmation toast: _"Policy settings updated successfully. Changes will apply to future calculations."_
   - New overdue fines calculated during the next nightly cron run will use the 3,000 VND rate; existing settled or accrued charges retain their historical amounts.
7. The flow resumes at Step 4 of the Basic Flow.

#### 2.2.2 Create a New Fixed-Duration Membership Plan

_Branching point: At Step 4 of the Basic Flow, under the "Membership Plans" tab, if the Librarian introduces a new membership tier._

1. The **Librarian (Admin)** clicks the "Add Membership Plan" button (`FR-MEM-09`).
2. The **System** presents a plan creation form with fields: `Plan Name`, `Duration (Days)`, `Price (VND)`, `Max Simultaneous Items`, `Allowed Loan Durations` (e.g., 7, 14, 21 days), `Allowed Renewals`, and `Can Reserve Books` (checkbox).
3. The **Librarian (Admin)** fills in the parameters (e.g., Name: _"Semester Plan"_, Duration: `120` days, Price: `60,000` VND, Max items: `5`, Loan durations: `[7, 14]`, Renewals: `2`, Can Reserve: `true`) and clicks "Create Plan".
4. The **System** validates that:
   - The plan name is unique.
   - Duration is $\ge 1$ day.
   - Price is $\ge 0$ VND.
   - Privilege limits are non-negative.
5. The **System** saves the new plan in the `membership_plans` configuration table (`is_active = true`).
6. The **System** writes a `settings_history` record logging the creation of the new plan.
7. The **System** displays a success toast. The new plan becomes immediately visible on the Reader Membership purchase screen (`/membership`) for future purchases (`TS-34`).
8. The flow resumes at Step 4 of the Basic Flow.

#### 2.2.3 Edit or Deactivate an Existing Membership Plan

_Branching point: At Step 4 of the Basic Flow, under the "Membership Plans" tab, if the Librarian edits pricing or deactivates a plan._

1. The **Librarian (Admin)** clicks "Edit" or "Deactivate" next to an existing membership plan (e.g., Academic Year Plan).
2. If editing (e.g., adjusting price from 150,000 VND to 180,000 VND):
   - The **Librarian (Admin)** inputs the new price and clicks "Update Plan".
   - The **System** saves the updated plan configuration and records the history row.
   - **Snapshot Immutability Rule:** All existing active memberships purchased under the former 150,000 VND rate retain their stored snapshot limits and terms until their original expiry date. Only new plan purchases reflect the 180,000 VND price (`FR-MEM-02`, `TS-34`).
3. If deactivating:
   - The **Librarian (Admin)** confirms deactivation.
   - The **System** sets `is_active = false`. The plan is hidden from prospective student purchases, but currently enrolled members continue until their expiration date.
4. The flow resumes at Step 4 of the Basic Flow.

#### 2.2.4 Validation Error on Invalid Setting Value or Out-of-Range Entry

_Branching point: At Step 4 of Alternative Flow 2.2.1 or Step 4 of Alternative Flow 2.2.2, if submitted values violate schema constraints._

1. The **Librarian (Admin)** enters an invalid value (e.g., a negative fine rate `-500`, a string into a numeric field, or a pickup window of `0` hours).
2. The **System** intercepts the submission during client/server validation.
3. The **System** aborts the database mutation and highlights the erroneous field with an inline validation message:
   - E.g., _"Daily fine rate must be a positive integer greater than or equal to 0."_
   - E.g., _"Pickup expiration window must be at least 1 hour."_
4. The **Librarian (Admin)** corrects the value or clicks "Cancel" to revert to the previously stored value.
5. The flow resumes at Step 4 of the Basic Flow.

#### 2.2.5 Inspect Immutable Settings Change History

_Branching point: At Step 4 of the Basic Flow, if staff reviews the chronological audit trail of configuration changes._

1. The **Librarian (Admin)** selects the "Settings Audit History" tab.
2. The **System** fetches rows from `settings_history` newest first.
3. The **Librarian (Admin)** reviews historical modifications, verifying who changed a specific policy, when the modification took place, and exact before/after JSON values.
4. The **Librarian (Admin)** can filter history by setting key or operator name.
5. The flow resumes at Step 5 of the Basic Flow.

## 3. Special Requirements

### 3.1 Centralized Settings Architecture (No Hardcoding)

- Every configurable library parameter, fine rate, duration, and limit must reside in the `settings` table (key `library`) and be managed through this interface (`FR-SET-01`, `Section 4.17`, Agent Rule 2).
- Hardcoded constants in application or backend code are strictly prohibited.

### 3.2 Future-Actions-Only Application and Snapshot Immutability

- Policy modifications apply strictly prospectively to future transactions (`FR-SET-01`).
- Existing memberships operate on their stored entitlement snapshots captured at purchase time (`FR-MEM-02`, `TS-34`). Existing loan fees and finalized overdue fines operate on their stored transaction values.

### 3.3 Comprehensive Type and Range Schema Validation

- Every key in the settings schema must have server-side Zod schema validation enforcing data types, minimum/maximum ranges, regex formats, and array structures. Invalid submissions must be rejected with descriptive error messages.

### 3.4 Immutable Audit Trail for Settings Changes

- Changes to any setting must automatically insert an immutable record into `settings_history` documenting operator ID, timestamp, key name, old value, and new value (`TS-58`).
- Database RLS rules must prohibit `UPDATE` and `DELETE` operations on `settings_history`.

### 3.5 Security and Role Verification

- Access to `/admin/settings` and configuration mutation endpoints is restricted exclusively to authenticated users with the `admin` role (`FR-AUTH-05`).

## 4. Preconditions

### 4.1 Admin Privileges Authenticated

The Librarian (Admin) possesses an active authenticated session with verified `admin` role privileges.

### 4.2 Configuration Database Online

The PostgreSQL database is active and the `settings` and `settings_history` tables are accessible.

---

## 5. Postconditions

### 5.1 Policy Settings Persisted

- The updated policy parameters are saved in the `settings` table.
- Future operations, cron calculations, and checkout routines immediately reference the updated values.

### 5.2 Audit History Recorded

- An immutable entry is written to `settings_history` detailing the operator, timestamp, old value, and new value.

### 5.3 Existing Records Protected by Immutability

- Historical loans, finalized fine charges, and active membership entitlements remain unaffected, preserving their original contractual terms.
