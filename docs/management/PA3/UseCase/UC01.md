## 1. Use-Case Name

**UC-01 - Register for library access** (Traces to: `FEAT-01`)

### 1.1 Brief Description

This use case allows a prospective Student (Reader) to self-register for a ShelfHelp library account using their university-issued email address and student identification number. Upon submitting valid registration details, the system creates an account in a pending verification state and dispatches a verification link via the external authentication and email service. Once the student verifies their email address, the account becomes active with the default `student` role, enabling self-service library discovery and borrowing without manual paper-based registration at the counter.

### 1.2 Actors

- **Primary Actor:** Student (Reader)
- **Supporting Actor:** Authentication and Email Service (Supabase Auth & SMTP/Email API)

## 2. Flow of Events

### 2.1 Basic Flow

This use case begins when an unregistered **Student** navigates to the ShelfHelp web application and chooses to create a new library account.

1. The **Student** clicks the "Register" (or "Create Account") link on the welcome or sign-in screen.
2. The **System** displays the Student Registration form containing input fields for `Full Name`, `Institutional Email`, `Student ID`, `Password`, and `Confirm Password`, along with a "Register" submit button.
3. The **Student** enters their `Full Name`, `Institutional Email` (e.g., `@student.hcmus.edu.vn`), `Student ID`, `Password`, and `Confirm Password`, and clicks the "Register" button.
4. The **System** validates the input format on the client and server (Zod schema validation), confirming that:
   - All required fields are populated.
   - The `Institutional Email` matches the permitted university domain.
   - The `Password` meets minimum security criteria and matches `Confirm Password`.
   - Neither the `Institutional Email` nor the `Student ID` is already registered to an existing account.
5. The **System** invokes the **Authentication and Email Service** (Supabase Auth) to create the user identity with `app_metadata.role` set to `student`, creates a corresponding record in the `profiles` table in a pending verification state, and sends an email containing a unique verification link to the provided `Institutional Email`.
6. The **System** displays a "Verification Email Sent" confirmation screen instructing the **Student** to check their university inbox and click the activation link, alongside a "Resend Verification Email" button.
7. The **Student** opens the verification email and clicks the activation link.
8. The **Authentication and Email Service** validates the verification token, marks the email as verified, and activates the student's profile (`status = active`).
9. The **System** redirects the **Student** to the Sign-In page (or authenticated Reader dashboard) and displays a confirmation message stating that the account has been verified and is ready for use. The use case ends.

### 2.2 Alternative Flows

#### 2.2.1 Invalid Institutional Email Domain

_Branching point: At Step 4 of the Basic Flow, if the submitted email address does not belong to the permitted university domain._

1. The **System** rejects the submission and highlights the `Institutional Email` field.
2. The **System** displays an inline validation message: _"Please register using a valid university-issued student email address."_
3. The **Student** corrects the `Institutional Email` field and resubmits the form.
4. The flow resumes at Step 4 of the Basic Flow.

#### 2.2.2 Duplicate Email or Student ID

_Branching point: At Step 4 of the Basic Flow, if the `Institutional Email` or `Student ID` already exists in the database._

1. The **System** aborts account creation and returns a conflict error.
2. The **System** displays an error message indicating that an account with the provided email or Student ID already exists, and provides quick navigation links to "Sign In" (`UC-02`) and "Forgot Password" (`UC-03`).
3. The **Student** either corrects a mistyped Student ID/email (resuming at Step 3 of the Basic Flow) or navigates to Sign In / Password Recovery, ending this use case.

#### 2.2.3 Weak Password or Password Mismatch

_Branching point: At Step 4 of the Basic Flow, if the password does not meet complexity rules or does not match the confirmation field._

1. The **System** highlights the `Password` and/or `Confirm Password` fields and displays the specific requirement that failed (e.g., minimum length or mismatch).
2. The **System** clears both password fields for security.
3. The **Student** re-enters a compliant password and confirmation.
4. The flow resumes at Step 3 of the Basic Flow.

#### 2.2.4 Verification Link Expired or Resend Requested

_Branching point: At Step 6 or Step 7 of the Basic Flow, if the verification email does not arrive or the student clicks an expired token link._

1. If the token is expired, the **System** displays an _"Activation link expired or invalid"_ message with a prompt to request a new link.
2. The **Student** clicks the "Resend Verification Email" button on the confirmation or error screen.
3. The **System** checks rate-limiting constraints, invalidates any previous verification token, and instructs the **Authentication and Email Service** to send a fresh verification link.
4. The **System** displays a toast notification confirming that a new verification email has been sent.
5. The flow resumes at Step 7 of the Basic Flow.

## 3. Special Requirements

### 3.1 Security and Access Control

- Passwords must never be stored or logged in plain text; they must be securely hashed by Supabase Auth.
- Role assignment (`student`) must be enforced server-side in `app_metadata.role` and protected by PostgreSQL Row-Level Security (RLS) so that a registering user cannot escalate their role to `librarian`/`admin` during sign-up (`FR-AUTH-05`, Constitution Principle II & VI).

### 3.2 Performance and Responsiveness

- Form submission and server-side validation should complete within 800 ms under normal operating conditions (`NFR` API latency target).
- The registration interface must follow a mobile-first responsive layout supporting viewport widths from 360 px to 1920 px.

### 3.3 Accessibility and Standards

- All form fields must include explicit labels, ARIA attributes for validation errors, full keyboard navigability, and a minimum text contrast ratio of 4.5:1 (WCAG 2.1 Level AA).

## 4. Preconditions

### 4.1 System and Network Availability

The ShelfHelp web application, Supabase PostgreSQL database, and the external Authentication and Email Service are online and reachable from the student's device.

### 4.2 Unauthenticated State

The Student is not currently signed into an active ShelfHelp session and possesses a valid university-issued student ID and institutional email account.

---

## 5. Postconditions

### 5.1 Account Created and Verified

- A new authentication identity exists in Supabase Auth with a verified email status.
- A corresponding record exists in the `profiles` table with the Student's full name, Student ID, institutional email, role set to `student`, and status set to `active`.
- The Student can immediately authenticate via `UC-02 (Sign in and sign out)`.

### 5.2 Registration Aborted or Pending

- If the Student abandons the form prior to Step 5, no user or profile record is persisted.
- If the Student completes Step 5 but has not yet completed Step 8, the account remains in an unverified state and cannot initiate borrowing or reservation transactions until email verification is completed.
