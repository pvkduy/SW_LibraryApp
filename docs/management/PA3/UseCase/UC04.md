## 1. Use-Case Name

**UC-04 - Manage personal profile** (Traces to: `FEAT-02`)

### 1.1 Brief Description

This use case enables an authenticated Student (Reader) or Librarian (Admin) to view and update their personal profile information (such as phone number and faculty details), modify their account password, and update their profile avatar by uploading an image or capturing one using the device camera with client-side cropping. Profile management ensures that contact information and visual identification remain accurate for automated notifications and counter verification.

### 1.2 Actors

- **Primary Actors:** Student (Reader), Librarian (Admin)
- **Supporting Actors:** Authentication Service (Supabase Auth), Storage Service (Supabase Storage Buckets)

---

## 2. Flow of Events

### 2.1 Basic Flow (Updating Contact Information)

This use case begins when an authenticated **User** navigates to their Account Settings or Profile page.

1. The **User** selects the "Profile" or "Account Settings" section from the application navigation menu.
2. The **System** retrieves the user's current profile data from the `profiles` table and displays current fields: `Full Name`, `Institutional Email` (read-only), `Student ID / Staff ID` (read-only), `Phone Number`, and `Faculty / Department`.
3. The **User** modifies their editable details (e.g., `Phone Number` or `Faculty`) and clicks the "Save Changes" button.
4. The **System** validates the input formats (e.g., phone number length and numeric patterns).
5. The **System** updates the corresponding record in the `profiles` table via a secure API call protected by PostgreSQL Row-Level Security (RLS).
6. The **System** displays a success notification confirming that the profile has been updated. The use case ends.

### 2.2 Alternative Flows

#### 2.2.1 Invalid Phone Number or Profile Data Format

_Branching point: At Step 4 of the Basic Flow, if the modified phone number or field contains invalid characters or incorrect length._

1. The **System** detects the validation error, aborts the database update, and highlights the invalid input field.
2. The **System** displays an inline error message (e.g., _"Please enter a valid phone number format"_).
3. The **User** corrects the invalid data and resubmits the form.
4. The flow resumes at Step 4 of the Basic Flow.

#### 2.2.2 Password Change within Profile

_Branching point: If the User initiates a password change action from the profile page._

1. The **User** selects the "Change Password" tab or button.
2. The **System** displays fields for `Current Password`, `New Password`, and `Confirm New Password`.
3. The **User** enters the requested passwords and clicks "Update Password".
4. The **System** verifies that `New Password` meets complexity rules and matches `Confirm New Password`.
5. The **System** invokes the **Authentication Service** to verify the `Current Password` and update the credential hash.
6. If verification succeeds, the **System** displays a success toast message and preserves the session. If the current password is incorrect, an error message (_"Incorrect current password"_) is displayed, prompting re-entry. The use case ends.

#### 2.2.3 Avatar Upload via File Selection

_Branching point: If the User chooses to update their profile picture by uploading an image file._

1. The **User** clicks the "Upload Avatar" button and selects an image file (PNG, JPG/JPEG) from their device.
2. The **System** validates the file size and mime type on the client side.
3. The **System** displays an interactive image cropping tool allowing the user to frame their photo.
4. The **User** confirms the cropped area, and the **System** uploads the processed image file to the `avatars` Supabase Storage bucket under an authenticated user path.
5. The **System** updates the `avatar_url` reference column in the user's `profiles` table record and refreshes the UI to display the new avatar. The use case ends.

#### 2.2.4 Camera Capture Avatar

_Branching point: If the User chooses to capture a new avatar using the device camera (mobile or desktop webcam)._

1. The **User** clicks the "Capture Photo" button.
2. The **System** requests browser permissions and activates the device camera hardware.
3. The **System** displays the camera preview feed with a capture shutter button.
4. The **User** frames themselves and clicks capture.
5. The **System** captures the frame, passes it to the client-side cropping tool, and proceeds with the upload and database record update identical to Steps 4–5 of Alternative Flow 2.2.3. The use case ends.

## 3. Special Requirements

### 3.1 Security and Row-Level Security (RLS)

- Profile modifications and avatar updates must be protected by PostgreSQL Row-Level Security (RLS) policies, ensuring users can only read and write their own profile rows (`auth.uid() = id`).
- Storage bucket policies for the `avatars` bucket must verify that upload paths match the user's unique identifier.

### 3.2 Client-Side Image Processing

- Avatar images must be cropped and compressed on the client side before transmission to minimize storage consumption and ensure fast page load times across mobile viewports.

### 3.3 Performance

- Profile updates and avatar rendering must complete with an asynchronous response time under 1.0 second.

### 5.3 Avatar Updated Successfully

- The new avatar image file is stored securely in Supabase Storage, and `profiles.avatar_url` points to the updated asset.
