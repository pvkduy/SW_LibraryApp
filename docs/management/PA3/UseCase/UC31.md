## 1. Use-Case Name

**UC-31 - Manage student accounts** (Traces to: `FR-SET-03`, `FR-AUTH-07`, `FR-AUTH-08`, `FR-MEM-07`, `FEAT-14`, `TS-29`, `TS-30`, `TS-32`, `TS-36`, `TS-59`)

### 1.1 Brief Description

This use case enables a Librarian (Admin) to search and inspect student accounts and perform account-status and membership actions. The student detail is a master–detail panel whose account history shows records of tier changes, account status (`active` / `restricted`), strikes, and their corresponding timestamps. Receipts are viewed on the Money screen. The detail panel exposes **four actions: Set Inactive, Restore (from Restricted), Membership refund/termination, and Register/renew membership**.

### 1.2 Actors

- **Primary Actor:** Librarian (Admin)
- **Supporting Actors:** Authentication Service (Supabase Auth API) & Audit Logger

---

## 2. Flow of Events

### 2.1 Basic Flow

This use case begins when an authenticated **Librarian (Admin)** opens the Student Directory (`/admin/students`).

1. The **Librarian (Admin)** navigates to "Students" in the back-office administration portal.
2. The **System** queries student profiles and displays the Student Directory as a master table–detail panel:
   - Search bar (by Full Name, Student ID, or Institutional Email).
   - Filter chips: Account Status (`active`, `restricted`, `inactive`, `pending_verification`) and Membership (`active member`, `non-member`).
   - Paginated table showing: Student Name, Student ID, Email, Faculty, Account Status badge, and Membership Tier.
3. The **Librarian (Admin)** clicks on a student row to open the detail panel.
4. The **System** writes an immutable audit entry `view_student` recording the admin's user ID, timestamp, and target student ID (`FR-SET-03`).
5. The **System** loads the Student Detail panel (`/admin/students/:uid`) showing:
   - **Profile:** Full name, ID, institutional email, phone, faculty, current status.
   - **Membership:** Current tier, entitlement summary, and purchase history.
   - **Simplified history:** records of tier changes, account status (`active` / `restricted`), strikes, and their timestamps. Receipts are viewed on the Money screen.
   - **Four actions:** ① Set Inactive · ② Restore (from Restricted) · ③ Membership refund/termination · ④ Register/renew membership.
6. The **Librarian (Admin)** reviews the student's status and history.
7. The **Librarian (Admin)** finishes review and returns to the directory or navigates away. The use case ends.

### 2.2 Alternative Flows

#### 2.2.1 Filter and Search Student Directory

_Branching point: At Step 2 of the Basic Flow, if the Librarian searches for a specific student or filters by risk indicators._

1. The **Librarian (Admin)** types a Student ID or partial name into the search bar, or selects a filter chip (e.g., "Status: Restricted" or "Debt: Has Debt").
2. The **System** applies indexed filters on `profiles` and derived debt/loan aggregations.
3. The **System** refreshes the directory table displaying only students matching the criteria.
4. The flow resumes at Step 3 of the Basic Flow.

#### 2.2.2 Set Account Inactive (POL-02 Checklist Validation)

_Branching point: At Step 5 of the Basic Flow, when a student graduates, withdraws, or is expelled and the Librarian initiates deactivation._

1. The **Librarian (Admin)** clicks "Set Inactive" on the student's detail panel.
2. The **System** evaluates the POL-02 checklist (no open items, no ready reservation, zero debt) and shows each failing condition.
3. If all pass, the **Librarian (Admin)** enters a required reason and confirms.
4. The **System** sets `inactive`, cancels waiting reservations, clears wishlist, terminates membership, bans the Auth user, and logs an audit entry.
5. The flow resumes at Step 6 of the Basic Flow.

#### 2.2.3 Restore a Restricted Account (Restoration Checklist §4.9)

_Branching point: At Step 5 of the Basic Flow, when a `restricted` account has resolved its lost-book case and the Librarian lifts the restriction._

1. The **Librarian (Admin)** opens a `restricted` student and clicks "Restore".
2. The **System** evaluates the §4.9 restore checklist (no lost item with empty `lost_resolved_at`, zero debt, no dispute flag) and enables Restore only when all pass.
3. The **Librarian (Admin)** enters a required verification note and confirms.
4. The **System** sets `restricted` → `active`, notifies the student, and logs an audit entry.
5. The flow resumes at Step 6 of the Basic Flow.

#### 2.2.4 Membership Refund or Termination (FR-MEM-07)

_Branching point: At Step 5 of the Basic Flow, if staff refunds or terminates an active membership._

1. The **Librarian (Admin)** clicks "Membership refund/termination" on the detail panel (`FR-MEM-07`).
2. The **System** prompts for a mandatory reason and confirms against the original membership receipt.
3. On confirm, the **System** creates a reversal receipt, sets the membership `terminated`, reverts the student to non-member entitlements immediately; existing loans keep due dates. Memberships cannot be transferred.
4. The flow resumes at Step 6 of the Basic Flow.

#### 2.2.5 Register or Renew Membership (Counter Transaction)

_Branching point: At Step 5 of the Basic Flow, if staff registers a new membership or renews an existing one at the counter (UC-05)._

1. The **Librarian (Admin)** clicks "Register/renew membership" on the detail panel.
2. The **System** shows the plan, eligibility, price, and effective start/end dates (with permitted stacking).
3. The **Librarian (Admin)** collects exact counter payment and confirms.
4. The **System** records a counter Payment, creates the `memberships` snapshot, and issues a receipt.
5. The flow resumes at Step 6 of the Basic Flow.

## 3. Special Requirements

### 3.1 Audit Logging for Student Record Access

- Opening any student detail view (`/admin/students/:uid`) must immediately record a `view_student` audit log entry containing the admin's identity, timestamp, and accessed student ID (`FR-SET-03`, `TS-59`).
- Modifying account status (`set_inactive`, `restore_student`, `reactivate_student`) requires mandatory notes and permanent audit logging (`FR-SYS-03`).

### 3.2 Restoration and Inactive Policy Rules (POL-02 & POL-09)

- Setting an account to `inactive` must be blocked by the server if any active loans, pending pickups, or debts exist.
- Restoring a `restricted` account must be blocked by the server until both Path A or Path B lost resolution is completed and the student has zero outstanding debt.

### 3.3 Membership Non-Transferability

- The system must never offer or allow transferring an active membership plan from one student account to another (`FR-MEM-07`).

### 3.4 Role Security and Privilege Separation

- Access to the student directory, detail inspection, and status mutation Edge Functions is restricted strictly to accounts with the `admin` role (`FR-AUTH-05`).

## 4. Preconditions

### 4.1 Admin Authentication

The Librarian (Admin) is authenticated with valid staff credentials holding the `admin` role.

### 4.2 Database and Authentication Provider State

The PostgreSQL database and Supabase Auth Admin services are reachable and healthy.

---

## 5. Postconditions

### 5.1 Student Directory Inspected (Audit Entry Written)

- A `view_student` audit log entry is recorded in the system audit table.

### 5.2 Account Status Updated

- If an action was performed, the student's profile status in `profiles` is transitioned to `inactive`, `active`, or `restricted`.
- Related reservation cancellations and membership terminations are finalized.

### 5.3 Authentication State Synchronized

- If set to `inactive`, the Supabase Auth user record is banned, terminating active user sessions.
- If restored or reactivated, the ban is cleared and normal student sign-in is re-enabled.
