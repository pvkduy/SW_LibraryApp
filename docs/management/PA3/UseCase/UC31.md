## 1. Use-Case Name

**UC-31 - Manage student accounts** (Traces to: `FR-SET-03`, `FR-AUTH-07`, `FR-AUTH-08`, `FR-MEM-07`, `FEAT-14`, `TS-29`, `TS-30`, `TS-32`, `TS-36`, `TS-59`)

### 1.1 Brief Description

This use case enables a Librarian (Admin) to search and inspect student accounts across the university library directory, review full account histories (demographics, active and past loans, debt status, financial charges, receipts, membership plans, and reservation strike records), and perform privileged account governance actions. Privileged actions include deactivating an account upon graduation or departure (`inactive`), restoring an account restricted due to past book loss after debt and copy clearance (`restricted` -> `active`), or processing membership refund and termination exceptions. Every student profile inspection and status alteration is securely recorded in the immutable system audit trail.

### 1.2 Actors

- **Primary Actor:** Librarian (Admin)
- **Supporting Actors:** Authentication Service (Supabase Auth API) & Audit Logger

## 2. Flow of Events

### 2.1 Basic Flow

This use case begins when an authenticated **Librarian (Admin)** opens the Student Directory (`/admin/students`).

1. The **Librarian (Admin)** navigates to "Students" in the back-office administration portal.
2. The **System** queries student profiles and displays the Student Directory page:
   - Search bar (by Full Name, Student ID, or Institutional Email).
   - Filter chips: Account Status (`active`, `restricted`, `inactive`, `pending_verification`), Outstanding Debt (`has debt`, `no debt`), Membership (`active member`, `non-member`), and Reservation Strikes (`has strikes`, `banned`).
   - Paginated table showing: Student Name, Student ID, Email, Faculty, Account Status badge, Debt balance, Membership Tier, and Reservation Strikes.
3. The **Librarian (Admin)** clicks on a student row to inspect the comprehensive account record.
4. The **System** writes an immutable audit entry `view_student` recording the admin's user ID, timestamp, and target student ID (`FR-SET-03`, `TS-59`).
5. The **System** loads the Student Detail screen (`/admin/students/:uid`) organized into tabs:
   - **Overview & Profile:** Full name, ID, institutional email, phone, faculty, account creation date, current status, debt hold flag, reservation ban end date.
   - **Circulation & Loans:** All current and historical loan items with copy barcodes, due dates, returned dates, and condition logs.
   - **Financial Ledger & Charges:** Accrued overdue fines, damage assessments, replacement fees, unpaid balance, and historical payment receipts (`RC-...`).
   - **Membership History:** Current plan status, start/end dates, purchase receipts, and entitlement snapshots.
   - **Reservation History:** Active queue positions, ready holds, expired holds, and recorded strike dates.
6. The **Librarian (Admin)** reviews the student's status and account history.
7. The **Librarian (Admin)** finishes review and returns to the directory or navigates away. The use case ends.

### 2.2 Alternative Flows

#### 2.2.1 Filter and Search Student Directory

_Branching point: At Step 2 of the Basic Flow, if the Librarian searches for a specific student or filters by risk indicators._

1. The **Librarian (Admin)** types a Student ID or partial name into the search bar, or selects a filter chip (e.g., "Status: Restricted" or "Debt: Has Debt").
2. The **System** applies indexed filters on `profiles` and derived debt/loan aggregations.
3. The **System** refreshes the directory table displaying only students matching the criteria.
4. The flow resumes at Step 3 of the Basic Flow.

#### 2.2.2 Set Student Account to Inactive (POL-02 Checklist Validation)

_Branching point: At Step 5 of the Basic Flow, when a student graduates, withdraws from the university, or is formally expelled, and the Librarian initiates account deactivation._

1. The **Librarian (Admin)** clicks the "Set Inactive" button on the student's detail action panel.
2. The **System** automatically evaluates the strict deactivation checklist (`POL-02`):
   - [x] No loan items in `awaiting_payment`, `payment_failed`, `ready_for_pickup`, `borrowed`, `overdue`, or `lost`.
   - [x] No reservation in `ready_for_pickup`.
   - [x] Outstanding debt balance is exactly 0 VND.
3. If all checklist criteria are satisfied (all checkmarks green):
   - The **System** enables the "Confirm Inactive" button and displays policy consequences: waiting reservations will be cancelled; wishlist entries cleared; active membership terminated without refund; authentication account suspended.
4. The **Librarian (Admin)** enters an administrative reason note (e.g., _"Student graduated - Class of 2026"_) and clicks "Confirm Inactive".
5. The **System** executes an atomic backend transaction:
   - Sets student profile status to `inactive`.
   - Cancels any reservations in `waiting` status.
   - Clears wishlist items.
   - Marks active membership as `terminated`.
   - Invokes Supabase Auth Admin API to ban the user (`banned_until = 'infinity'`), invalidating active authentication tokens.
   - Logs an audit entry `set_inactive` with operator ID, target student ID, and explanation note (`FR-SYS-03`).
6. The **System** displays a confirmation toast and updates the account status badge to "Inactive".
7. The flow resumes at Step 6 of the Basic Flow.

#### 2.2.3 Set Inactive Blocked by Unresolved Library Commitments

_Branching point: At Step 2 of Alternative Flow 2.2.2, if any deactivation condition fails._

1. The **System** evaluates the checklist and identifies failing conditions (e.g., 1 borrowed book remains unreturned, or outstanding debt equals 15,000 VND).
2. The **System** disables the "Confirm Inactive" button and renders clear visual alerts for each failing requirement:
   - E.g., _"Cannot deactivate account: 1 item not returned (Barcode: C-0045) [View Loan]"_
   - E.g., _"Cannot deactivate account: Outstanding debt of 15,000 VND pending settlement [View Charges]"_
3. Each failing item provides a direct link to the respective Loan or Financial charge tab.
4. The **Librarian (Admin)** reviews the pending obligations and closes the modal to address the outstanding items first.
5. The use case ends without modifying the student's status.

#### 2.2.4 Restore a Restricted Account Following Lost-Book Resolution

_Branching point: At Step 5 of the Basic Flow, if an account was automatically set to `restricted` due to a lost book (`DEC-17`, `POL-09`), and the student has resolved the issue._

1. The **Librarian (Admin)** opens a student detail page whose status is `restricted`.
2. The **System** displays the "Account Restricted" warning banner along with the automated **Restoration Checklist** (`FR-AUTH-08`, `Section 4.9`):
   - Check 1: No Loan Item in `lost` with `lost_resolved_at` empty. (Satisfied if the student returned the lost copy under Path A, or paid the replacement charge under Path B).
   - Check 2: Total outstanding debt is exactly 0 VND.
   - Check 3: No unresolved write-off or dispute flag.
3. If all checklist conditions pass:
   - The **System** enables the "Restore Account" action button.
4. If any condition fails (e.g., replacement charge remains unpaid):
   - The "Restore Account" button remains disabled with explanations of outstanding obligations.
5. The **Librarian (Admin)** enters a mandatory verification note (e.g., _"Lost book returned in acceptable condition via Path A; replacement charge refunded and fines cleared"_) and clicks "Restore Account".
6. The **System** processes the restoration:
   - Updates the profile status from `restricted` to `active`.
   - Clears restriction flags on the student session.
   - Sends an in-app and email notification to the student informing them that full borrowing privileges have been restored.
   - Logs an audit entry `restore_student` with operator ID, target student ID, and verification notes.
7. The **System** updates the profile badge to "Active" and displays a success notification.
8. The flow resumes at Step 6 of the Basic Flow.

#### 2.2.5 Process Membership Exception, Termination, or Refund

_Branching point: At Step 5 of the Basic Flow, under the "Membership History" tab, if staff must terminate or refund an active membership due to an administrative exception._

1. The **Librarian (Admin)** selects the "Membership History" tab and clicks "Refund & Terminate Membership" (`FR-MEM-07`).
2. The **System** prompts the Librarian for a mandatory reason and confirms the reversal details against the original membership payment receipt (`FR-RCPT-05`).
3. The **Librarian (Admin)** enters the justification and clicks "Confirm Reversal".
4. The **System** generates a negative reversal receipt (`reverses_receipt_id`), transitions the membership status to `terminated`, and immediately reverts the student's borrowing entitlements to non-member limits.
5. Any existing active loans keep their original due dates (`FR-MEM-07`, `DEC-23`).
6. The **System** notes that memberships cannot be transferred to another student.
7. The flow resumes at Step 6 of the Basic Flow.

#### 2.2.6 Reactivate an Inactive Account

_Branching point: At Step 5 of the Basic Flow, if an `inactive` student re-enrolls or returns to the university._

1. The **Librarian (Admin)** views an `inactive` account and clicks "Reactivate Account".
2. The **System** confirms that the student possesses a valid institutional email and student ID.
3. The **Librarian (Admin)** enters an administrative justification note and confirms reactivation.
4. The **System** updates profile status to `active`, unbans the Supabase Auth identity, and logs an audit entry.
5. The student is notified and can authenticate again via `UC-02`.
6. The flow resumes at Step 6 of the Basic Flow.

## 3. Special Requirements

### 3.1 Audit Logging for Student Record Access

- Opening any student detail view (`/admin/students/:uid`) must immediately record a `view_student` audit log entry containing the admin's identity, timestamp, and accessed student ID (`FR-SET-03`, `TS-59`).
- Modifying account status (`set_inactive`, `restore_student`, `reactivate_student`) requires mandatory notes and permanent audit logging (`FR-SYS-03`).

### 3.2 Restoration and Inactive Policy Rules (POL-02 & POL-09)

- Setting an account to `inactive` must be blocked by the server if any active loans, pending pickups, or debts exist.
- Restoring a `restricted` account must be blocked by the server until both Path A or Path B lost resolution is completed and the student has zero outstanding debt.

### 3.3 Membership Non-Transferability

- The system must never offer or allow transferring an active membership plan from one student account to another (`FR-MEM-07`).

### 3.4 Role Security and Privilege Separation

- Access to the student directory, detail inspection, and status mutation Edge Functions is restricted strictly to accounts with the `admin` role (`FR-AUTH-05`).

## 4. Preconditions

### 4.1 Admin Authentication

The Librarian (Admin) is authenticated with valid staff credentials holding the `admin` role.

### 4.2 Database and Authentication Provider State

The PostgreSQL database and Supabase Auth Admin services are reachable and healthy.

---

## 5. Postconditions

### 5.1 Student Directory Inspected (Audit Entry Written)

- A `view_student` audit log entry is recorded in the system audit table.

### 5.2 Account Status Updated

- If an action was performed, the student's profile status in `profiles` is transitioned to `inactive`, `active`, or `restricted`.
- Related reservation cancellations and membership terminations are finalized.

### 5.3 Authentication State Synchronized

- If set to `inactive`, the Supabase Auth user record is banned, terminating active user sessions.
- If restored or reactivated, the ban is cleared and normal student sign-in is re-enabled.
