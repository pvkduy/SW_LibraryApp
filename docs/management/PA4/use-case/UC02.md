## 1. Use-Case Name

**UC-02 - Sign in and sign out** (Traces to: `FEAT-01`, `FR-AUTH-03`)

### 1.1 Brief Description

This use case enables an authenticated user—either a Student (Reader) or a Librarian (Admin)—to start or end an authenticated session in the ShelfHelp web application. Upon sign-in, the system verifies the user's credentials via the authentication service, applies a temporary lockout after repeated failures, checks the user's account status and role (`app_metadata.role`), and routes the user to either the mobile-first Reader Mode or the desktop-first Admin Mode. The User may optionally select **"Keep me signed in"** to persist the session across browser restarts without ever storing the password. Upon sign-out, the system revokes the session token and returns the user to the public sign-in view; the account menu also links to **Active Sessions (`UC-32`)** for reviewing and remotely revoking sessions on other devices.

### 1.2 Actors

- **Primary Actors:** Student (Reader), Librarian (Admin)
- **Supporting Actor:** Authentication and Email Service (Supabase Auth)

## 2. Flow of Events

### 2.1 Basic Flow

This use case starts when an unauthenticated **User** (Student or Librarian) navigates to the ShelfHelp application to start an authenticated session.

1. The **User** selects the "Sign In" option on the navigation bar or landing page.
2. The **System** displays the Sign-In form requesting `Email` and `Password`, a **"Keep me signed in"** checkbox (unchecked by default), a "Sign In" button, and navigation links to "Register" (`UC-01`) and "Forgot Password" (`UC-03`).
3. The **User** enters their `Email` and `Password`, optionally selects "Keep me signed in", and clicks the "Sign In" button.
4. The **System** validates the input format (non-empty fields, email syntax, and password length) and submits the credentials to the **Authentication and Email Service** (Supabase Auth).
5. The **Authentication and Email Service** applies the server-side failed-attempt policy (Section 3.5). If the identifier or client is currently locked, it rejects the attempt with HTTP 429 and a `Retry-After` value; the flow continues at Alternative Flow 2.2.3.
6. The **Authentication and Email Service** verifies the credentials and returns an encrypted session token (JWT) containing `app_metadata.role`.
7. The **System** resets the failed-attempt counter for the identifier and client, applies the session-persistence choice described in Alternative Flow 2.2.7, and fetches the caller's record from the `profiles` table to verify `profiles.status`.
8. The **System** initializes the authenticated client session and routes the **User** according to their role:
   - If `role = student`: The **System** loads the Reader Mode interface (Catalog / Home dashboard).
   - If `role = librarian` (or `admin`): The **System** loads the Admin Mode interface (Circulation & Inventory dashboard).
9. The use case ends with an active authenticated session.

### 2.2 Alternative Flows

#### 2.2.1 Sign Out of an Active Session

_Branching point: Occurs at any time after Step 8 of the Basic Flow while the User has an active session._

1. The **User** clicks the "Sign Out" (or "Logout") button in the account menu or navigation header.
2. The **System** calls the **Authentication and Email Service** to invalidate the current refresh and access tokens and clears local session state, persisted session tokens, and cached user data.
3. The **System** redirects the **User** to the Sign-In screen and displays a confirmation message. The use case ends.
4. To terminate sessions on other devices, the **User** opens "Active Sessions" in the account menu and continues with `UC-32` (Manage active sessions).

#### 2.2.2 Invalid Email or Password

_Branching point: At Step 6 of the Basic Flow, if the email does not exist or the password does not match._

1. The **Authentication and Email Service** rejects the authentication attempt and records one failed attempt for the submitted identifier and the client IP address.
2. The **System** clears the `Password` field and displays a generic error message: _"Invalid email or password. Please try again."_ (avoiding account enumeration).
3. If the failed-attempt count is below the threshold in Section 3.5, the **User** may re-enter their credentials (resuming at Step 3 of the Basic Flow) or select "Forgot Password" (`UC-03`).
4. If the threshold is reached, the flow continues at Alternative Flow 2.2.3.

#### 2.2.3 Temporary Lockout After Repeated Failures

_Branching point: At Step 5 of the Basic Flow, or after Step 4 of Alternative Flow 2.2.2, when the same account identifier or client has accumulated the configured number of consecutive failures._

1. The **Authentication and Email Service** rejects the attempt without verifying the password, even if the supplied password is correct, and returns HTTP 429 with a `Retry-After` value.
2. The **System** displays: _"Too many failed sign-in attempts. Please try again in 10 minutes."_ together with a countdown, and disables the "Sign In" button until the lockout expires.
3. The lockout is enforced server-side. Reloading the page, clearing browser storage, or switching between email and Student ID does not bypass it.
4. After 10 minutes the lockout expires automatically and the failed-attempt counter resets. A successful sign-in or a successful password reset (`UC-03`) also clears the counter.
5. The **User** may wait for the countdown to finish (resuming at Step 2 of the Basic Flow) or use "Forgot Password" (`UC-03`). The use case ends if the User leaves the Sign-In screen.

#### 2.2.4 Unverified Student Email

_Branching point: At Step 6 of the Basic Flow, if the Student's email address has not yet been verified._

1. The **System** blocks session creation and displays a notice: _"Your email address is not yet verified. Please check your university inbox for the activation link."_
2. The **System** displays a "Resend Verification Email" button.
3. If the **User** clicks "Resend Verification Email", the **System** requests a new verification email from the **Authentication and Email Service**. The use case ends.

#### 2.2.5 Restricted or Deactivated Account

_Branching point: At Step 7 of the Basic Flow, when inspecting `profiles.status`._

1. **If `profiles.status = deactivated` (or suspended):**
   - The **System** immediately terminates the session (`ACCOUNT_NOT_ACTIVE`), displays an error message instructing the user to contact the library service desk, and returns to Step 2 of the Basic Flow.
2. **If `profiles.status = restricted` (due to chronic overdue/lost book or unpaid debt):**
   - The **System** allows the **Student** to sign into Reader Mode so they can view their loans, charges, and receipts (`UC-11`, `UC-13`, `UC-18`), but displays a prominent restriction banner and disables checkout and reservation actions.

#### 2.2.6 Session Expiration

_Branching point: During an active session, if both the access token and refresh token expire, or if the session is revoked from another device (`UC-32`, Alternative Flow 2.2.4)._

1. The **System** detects an unauthorized/expired token response on the next protected route or Edge Function call.
2. The **System** clears the local session state and any persisted refresh token, redirects the **User** to the Sign-In screen with the notice _"Your session has expired. Please sign in again"_ (or the remote-revocation notice defined in `UC-32`), and resumes at Step 2 of the Basic Flow.

#### 2.2.7 Persistent Session ("Keep Me Signed In")

_Branching point: At Step 3 of the Basic Flow, if the User selects the "Keep me signed in" checkbox._

1. The **System** requests a session with a long-lived refresh token from the **Authentication and Email Service** and configures the client to persist that refresh token in browser storage (`localStorage`) while keeping the access token in memory.
2. On a later visit within the refresh-token lifetime, the **System** silently refreshes the session and routes the **User** by role without asking for credentials again.
3. If the checkbox is **not** selected, the refresh token is kept in `sessionStorage` and discarded when the browser tab or window closes (or at the Auth service's normal session lifetime).
4. On shared or public devices, the **User** should leave the checkbox unchecked; the Sign-In screen displays a short hint to that effect.
5. "Sign Out" (2.2.1) and remote revocation (`UC-32`) remove the persisted refresh token. If the token expires or is revoked, the **System** clears it and shows the Sign-In screen.
6. The **System** never stores the User's password; see Section 3.4.

## 3. Special Requirements

### 3.1 Role-Based Access Control (RBAC)

- Role separation between `student` and `librarian`/`admin` must be enforced across four layers: frontend route guards, PostgreSQL Row-Level Security (RLS) policies, Supabase Edge Function checks, and Storage policies (`FR-AUTH-05`, Constitution Principle II).
- A Student attempting to access an Admin route or invoke an Admin Edge Function must be denied with `FORBIDDEN_ROLE` (HTTP 403).

### 3.2 Performance

- Sign-in and sign-out operations must complete with an average API response time of no more than 800 ms under normal operating conditions.
- The active-session list used by `UC-32` must load within 1 second for a user with up to 20 sessions.

### 3.3 Security and Session Management

- All authentication requests must be transmitted over HTTPS, using secure password hashing, short-lived JWT access tokens, and automatic session refresh mechanisms.
- Every Edge Function must re-verify `profiles.status` on the server so a newly deactivated account is blocked immediately even if an older JWT has not yet expired.
- Failed-attempt counters and lockout state must be stored and enforced server-side; a client-side timer alone is not an acceptable control.
- Sign-out, password reset, account deactivation, and remote session revocation must invalidate the affected refresh tokens so the session cannot be silently renewed.
- Session metadata (device, browser, IP address, last-active time) may be shown only to the owner of the session; it must never expose raw tokens, password hashes, or another user's data.

### 3.4 Credential Handling and "Remember Me" on the Web

- **The application must never store the User's password** in `localStorage`, `sessionStorage`, IndexedDB, cookies, application state, or logs. "Remember credentials" is implemented as a persistent session, not as password storage.
- **Recommended interpretation — "Keep me signed in":** persist only the Auth service's refresh token/session. With the Supabase client this means `persistSession: true`, `autoRefreshToken: true`, and `storage: window.localStorage` when the checkbox is selected, or `storage: window.sessionStorage` when it is not. The access token remains in memory and is refreshed automatically. The refresh token is an opaque, revocable credential; it is not the password.
- **Safer alternative — "Remember my email":** if the product only needs to avoid retyping the identifier, persist only the email address or Student ID in `localStorage` and prefill the identifier field. Never prefill or persist the password.
- **Browser password managers:** use a real `<form>` with `autocomplete="username"` and `autocomplete="current-password"` (and `autocomplete="new-password"` on registration and reset forms) so the browser can offer to save or autofill credentials. The application must not read from or write to the browser's credential store.
- **Token storage risk:** for the current single-page application, `localStorage` is acceptable only with a strict Content Security Policy, no untrusted third-party scripts, and dependency scanning (`NFR-06`). If the deployment later adds a backend-for-frontend or server-side rendering, prefer `HttpOnly; Secure; SameSite=Lax` cookies for the refresh token with CSRF protection.
- **Shared and lost devices:** provide a visible "Sign out all other sessions" action through `UC-32`, and clear persisted tokens on sign-out and on the Auth service's `SIGNED_OUT` event.

### 3.5 Failed-Attempt Throttling and Lockout

- **Default policy:** after **5 consecutive failed sign-in attempts** for the same account identifier (email or Student ID) within **15 minutes**, the identifier is locked for **10 minutes**. The thresholds are configuration values, not hard-coded client constants.
- The same policy must apply whether the User signs in with an email address or a Student ID, and the lockout key must cover both forms of the same account.
- A per-IP or per-device rate limit must run alongside the per-identifier lockout to slow password spraying across many accounts. Because a pure account lockout can be abused for denial of service, the system should also consider a CAPTCHA challenge before the lockout threshold.
- Lockout responses must be generic and must not reveal whether the email/Student ID exists or whether the password was correct. The response includes `Retry-After` so the client can show an accurate countdown.
- A successful sign-in or a successful password reset (`UC-03`) clears the failed-attempt counter for that identifier. The lockout must not block the password-recovery flow.
- Security events (failed attempt, lockout start, lockout expiry, successful sign-in) should be recorded in the audit log without recording passwords or tokens.

## 4. Preconditions

### 4.1 System and Network Availability

The ShelfHelp web application, PostgreSQL database, and Supabase Auth service are online and accessible.

### 4.2 Existing User Account

For sign-in, the User possesses a registered Student account (created via `UC-01`) or a pre-provisioned Librarian/Admin account. For sign-out, the User has an active authenticated session.

### 4.3 No Active Sign-In Lockout

The User's account identifier and client are not currently inside a temporary lockout window (Section 3.5). If they are, Alternative Flow 2.2.3 applies.

## 5. Postconditions

### 5.1 Successful Sign-In

- An encrypted session is active, and the User is routed to the appropriate interface (`Reader Mode` or `Admin Mode`) with permissions matching `app_metadata.role` and `profiles.status`.
- The failed-attempt counter for the identifier and client is reset.

### 5.2 Successful Sign-Out

- The session token is revoked, persisted session tokens and cached private data are cleared from the browser, and protected routes are no longer accessible without re-authenticating.

### 5.3 Failed Sign-In

- No authenticated session is established, the User remains in an unauthenticated state, and the failed-attempt counter is incremented.

### 5.4 Temporary Lockout

- No authenticated session is established, the identifier/client is locked for 10 minutes, and further attempts are rejected with a generic message and a `Retry-After` value until the lockout expires.

### 5.5 Persistent Session

- When "Keep me signed in" is selected, a revocable refresh token is persisted in browser storage according to Section 3.4; the User's password is never persisted.
