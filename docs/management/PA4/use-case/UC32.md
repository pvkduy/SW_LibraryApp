## 1. Use-Case Name

**UC-32 - Manage active sessions** (Traces to: `FEAT-01`, `FR-AUTH-03`, `FR-AUTH-04`, `FR-PROF-02`)

### 1.1 Brief Description

This use case enables an authenticated Student (Reader) or Librarian (Admin) to review the devices and browser sessions currently signed in to their ShelfHelp account, and to remotely sign out any session they no longer trust. It is the account-security companion to the sign-out flow in `UC-02`: instead of ending only the current session, the User can see all active sessions, identify the current one, revoke a single other session, or sign out all other sessions at once. This is the recovery path when a device is lost, a shared computer was left signed in, or the User suspects that a refresh token was stolen.

### 1.2 Actors

- **Primary Actors:** Student (Reader), Librarian (Admin)
- **Supporting Actor:** Authentication Service (Supabase Auth session store and admin API)

## 2. Flow of Events

### 2.1 Basic Flow

This use case begins when an authenticated **User** wants to review or revoke the sessions associated with their own account.

1. The **User** opens access **"Active Sessions"** from the Porfile screen
2. The **System** calls a server-side session-inventory endpoint with the User's current JWT. The endpoint derives the user identity from the JWT and returns only the sessions that belong to that user.
3. The **System** displays the session list, sorted by most recent activity, with the following information for each entry:
   - A **"This device"** badge on the current session;
   - A human-readable device and browser description derived from the user agent;
   - The approximate IP address or coarse location, when available;
   - The sign-in time and the last-active time;
   - A **"Sign Out"** action for every other session.
4. The **User** selects **"Sign Out"** next to a session that is not the current session.
5. The **System** displays a confirmation dialog naming the device and sign-in time, and warns that the device will need to sign in again.
6. The **User** confirms the revocation.
7. The **System** sends the opaque session identifier to the revocation endpoint. The endpoint verifies that the session belongs to the caller, revokes the session's refresh tokens, and records the security event in the audit log.
8. The **System** removes the revoked session from the list and displays a success notification: _"That device has been signed out."_
9. The use case ends.

### 2.2 Alternative Flows

#### 2.2.1 Sign Out All Other Sessions

_Branching point: At Step 4 of the Basic Flow, if the User chooses the bulk action instead of a single row._

1. The **User** selects **"Sign Out All Other Sessions"**.
2. The **System** displays a confirmation dialog listing the number of sessions that will be revoked and stating that the current session will remain active.
3. The **User** confirms.
4. The **System** asks the Authentication Service to revoke every session for the caller except the current one, then refreshes the list and displays: _"All other devices have been signed out."_
5. The use case ends. This flow is recommended after a password change, after using a shared computer, or after the User discovers an unrecognized device.

#### 2.2.2 Session Already Expired or Revoked

_Branching point: At Step 7 of the Basic Flow, if the selected session no longer exists because it expired or was revoked elsewhere._

1. The **Authentication Service** reports that the session is not found or already revoked.
2. The **System** treats the outcome as success (revocation is idempotent), removes the stale row, and displays: _"This session was already signed out."_
3. The use case ends.

#### 2.2.3 Revocation Fails or Network Error

_Branching point: At Step 7 of the Basic Flow, if the revocation endpoint returns a server error or the request times out._

1. The **System** keeps the session in the list and displays an error: _"We could not sign out that device. Please try again."_
2. The **User** may retry the revocation (resuming at Step 5) or use "Sign Out All Other Sessions" (2.2.1).
3. The **System** must not remove the row or show a success message until the Authentication Service confirms the revocation.

#### 2.2.4 Current Session Revoked from Another Device

_Branching point: During an active session, when another device or an administrator revokes the User's current session._

1. On the next protected request or token refresh, the **System** receives an unauthorized response because the refresh token is no longer valid.
2. The **System** clears local session state and any persisted refresh token, and redirects the **User** to the Sign-In screen with the notice: _"Your session was signed out on another device. Please sign in again."_
3. The flow continues at `UC-02`, Basic Flow Step 2.

#### 2.2.5 Unrecognized Session (Possible Compromise)

_Branching point: At Step 3 of the Basic Flow, if the User does not recognize a device or sign-in time._

1. The **User** signs out the unrecognized session (Basic Flow Steps 4–8) and, if other unfamiliar sessions remain, uses "Sign Out All Other Sessions" (2.2.1).
2. The **System** displays a security recommendation: change the password (`UC-04`) and review recent account activity.
3. The **User** may open the password-change flow (`UC-04`, Alternative Flow 2.2.2) or end the use case.

#### 2.2.6 Session List Unavailable

_Branching point: At Step 2 of the Basic Flow, if the Authentication Service or the session-inventory endpoint is unavailable._

1. The **System** displays an error: _"Active sessions are temporarily unavailable. You can still sign out of this device."_
2. The **System** offers a **"Sign Out This Device"** action that continues with `UC-02`, Alternative Flow 2.2.1, and a **"Retry"** action that repeats Step 2.
3. The use case ends if the User signs out or leaves the screen.

#### 2.2.7 Sign Out the Current Session

_Branching point: At Step 4 of the Basic Flow, if the User selects the row marked "This device"._

1. The **System** does not revoke the session through the remote-session endpoint. Instead, it hands off to `UC-02`, Alternative Flow 2.2.1 (Sign Out of an Active Session).
2. The **System** clears local state and redirects the **User** to the Sign-In screen. The use case ends.

## 3. Special Requirements

### 3.1 Authorization and Privacy

- The session-inventory and revocation endpoints must derive the caller's identity from the verified JWT. They must never accept a `user_id` or session owner from the request body, and they must return only the caller's own sessions.
- Session identifiers are opaque to the client. The response must not include refresh tokens, access tokens, password hashes, or service-role keys.
- IP addresses and user-agent strings are personal data. They are shown only to the session owner, are truncated where practical, and are not exposed to other users or included in analytics exports.
- A Librarian (Admin) may manage only their own sessions through this use case. Viewing or terminating another user's sessions is not part of UC-32; account-wide suspension is handled by `UC-31`, which revokes the affected user's sessions as a side effect.
- The endpoint must run server-side (for example, a Supabase Edge Function using the service role) because the Auth session table is not exposed to the browser through PostgREST. The service-role key must never reach the client.

### 3.2 Session Metadata and Freshness

- The session inventory is based on the Authentication Service's session records (for example, `auth.sessions`, which provides the session ID, creation time, last update, IP address, and user agent).
- "Last active" may be updated at a coarse interval, so the list is eventually consistent. The interface must show relative times (for example, "2 hours ago") and must not claim real-time precision.
- If the user agent or IP address is missing, the interface shows "Unknown device" or "Unknown location" instead of an empty row.
- The current session must be identified by comparing the session ID associated with the caller's JWT, not by guessing from the user agent.

### 3.3 Revocation Semantics

- Revoking a session invalidates its refresh token. The short-lived access token may remain valid until it expires; sensitive Edge Functions must therefore re-verify account status and, where required, session validity on the server.
- If immediate termination is required, the server may maintain a short-lived session denylist or check the Authentication Service's session record before executing sensitive commands.
- "Sign Out All Other Sessions" must never revoke the current session. Ending the current session is the responsibility of `UC-02`.
- Revocation is idempotent: revoking an already-revoked session succeeds without an error and without creating duplicate audit entries.
- Every revocation must be audit-logged with the actor, session identifier (or a hash of it), timestamp, and outcome. Passwords and tokens must never be logged.

### 3.4 Performance

- The session list must load within 1 second for a user with up to 20 active sessions under normal operating conditions.
- A single-session revocation must complete within 800 ms on average; "Sign Out All Other Sessions" must complete within 2 seconds for up to 20 sessions.
- The interface must remain usable while the list is loading and must not block navigation to other account settings.

### 3.5 Accessibility and Usability

- The session list must be exposed as a semantic list or table with column headers, and every "Sign Out" action must have an accessible name that includes the device and sign-in time.
- Confirmation dialogs must trap focus, be dismissible with the Escape key, and return focus to the triggering control.
- The interface must meet WCAG 2.1 Level AA contrast and keyboard-navigation requirements.
- Destructive actions must be visually distinct from navigation actions and must never be the default focused control in a confirmation dialog.

## 4. Preconditions

### 4.1 Active Authenticated Session

The User has an active authenticated session in ShelfHelp (`UC-02`) and is signed in as a Student (Reader) or Librarian (Admin).

### 4.2 Session Inventory Available

The Authentication Service exposes session records for the caller, and the server-side session-inventory and revocation endpoints are deployed and reachable. The service-role credentials used by those endpoints are stored only in the server environment.

---

## 5. Postconditions

### 5.1 Session Revoked

- The selected session's refresh token is invalid, so the next refresh attempt from that device fails and the device is returned to the Sign-In screen.
- The revoked session no longer appears in the caller's session list, and the security event is recorded in the audit log.

### 5.2 All Other Sessions Revoked

- Every session except the current one is revoked, the current session remains active, and the list shows only "This device".

### 5.3 Revocation Not Completed

- If the request fails, the session remains active, the list is unchanged, and the User sees an error with a retry option. No success message is shown.

## 6. Extension Points

### 6.1 None

There are no extension points for this use case.

> **Related use cases.** `UC-02` signs the current session in and out; `UC-03` and `UC-04` change the password and should revoke other sessions; `UC-31` lets an administrator change another user's account status. UC-32 covers only the caller's own sessions.
